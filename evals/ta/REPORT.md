# Jeffy eval: bukosabino/ta

**Target**: [bukosabino/ta](https://github.com/bukosabino/ta) (5,129 stars, verified via `gh api repos/bukosabino/ta` on 2026-07-27) at HEAD `a890410710a6e483c9ba08da7f3dd5089e4b9dff`, dated 2026-03-18 - a README-only commit. The last commit that touched any Python is `5654782`, 2023-11-02; the released artifact on PyPI is `ta` 0.11.0, uploaded 2023-11-02. Audited on CPython 3.13.8 against pandas 3.0.5 / numpy 2.5.1 and re-run against pandas 2.2.3, in a local clone. Nothing was pushed upstream, no issue or PR was opened.

**The frame**: `ta` is a library consumed programmatically. A trader hands it an OHLC DataFrame - in practice a datetime-indexed one - and writes the returned Series straight back into that frame. There is no UI, no network surface, no untrusted input. The only thing that can really hurt a user here is a wrong number returned without complaint, so that is what this audit went looking for.

**The headline**: it found two. Parabolic SAR returns wrong values, and a wrong number of rows, on every frame whose index is not a plain `RangeIndex` - which includes every datetime-indexed frame and, worse, the exact frame the project's own README quickstart tells you to build. KST fabricates 30 warm-up rows out of a whole-series average, so those rows are computed from prices that have not happened yet. Both were reproduced on the library's own shipped 46,306-bar dataset. The project's 134-test suite cannot see either one, and that is not bad luck: all 32 of its fixtures are `pd.read_csv(...)` with a default RangeIndex, and 134 of its assertion lines are on `.tail(` with not one on `.head(`.

## Findings

**TA-1 (High, correctness) - Parabolic SAR mixes label-based and positional writes on the same Series.** `ta/trend.py:1030` at HEAD writes `self._psar[i] = high2`; `ta/trend.py:1032`, the very next branch, writes `self._psar.iloc[i] = high1`. `self._psar` is `self._close.copy()` (`ta/trend.py:977`), so it carries the caller's index, and `i` is a loop counter - a position. Following the README's quickstart verbatim on the library's own `test/data/datas.csv` (46,306 bars): after `ta.utils.dropna(df)`, which the README tells you to call and which leaves a gapped integer index, `psar()` returned **46,465 rows for a 46,306-row input** - 159 rows appended at labels that happened not to exist - with **9,408 of 46,306 rows wrong**, max absolute error **3,410.89** price units (2,132.6 percent). On a DatetimeIndex: 47,455 rows out, 8,601 wrong, max error 284.48 (55.7 percent), and the index degrades to `object` dtype. `psar_up()` and `psar_down()` - the ones `add_all_ta_features` actually writes into your frame - keep their length and are wrong on 3,133 and 6,353 rows. Across 50 synthetic price paths, 48 diverged. The version story matters: on pandas 2.2.3 the DatetimeIndex case still worked and merely emitted the `FutureWarning` of issue #348, so issue #348 was the last audible warning before the failure went silent; on pandas 3.0.5 the deprecation has completed and the write silently enlarges the Series instead. The gapped-integer case has been silently wrong on every pandas version, warning-free, because there the label reading is unambiguous. Issues #354 and #348. **How fixed**: `PSARIndicator._run` now runs the whole recursion on numpy buffers and constructs `_psar`, `_psar_up` and `_psar_down` once at the end, so no step in the loop can be reinterpreted as a label lookup. Filed and fixed at the boundary rather than as a one-character patch, per the class rule.

**TA-2 (High, correctness) - KST computes 30 of its output rows from prices that have not happened yet.** `ta/trend.py:500,502,511,513,522,524,533,535` pass `fill_value=self._close.mean()` to the four `shift()` calls, substituting a whole-series average for the missing warm-up history. Reproduced by truncation: on a 400-bar path, `kst()` row 14 reads **-73.490631** computed over all 400 bars and **-16.020814** computed over the first 200 of the same bars. 30 of the first 200 rows change; 38 change for `kst_sig()`. Those rows should not exist at all - the first mathematically defined KST bar is row 44, `max(roc_i + window_i) - 1`, so the library emits 30 fabricated values before its own indicator is defined. For a library whose stated purpose is feature engineering on financial time series, a walk-forward backtest reading those rows is trading on the future. **How fixed**: `fill_value` removed at all 14 sites of the idiom in `ta/trend.py`, so the warm-up is NaN like every other indicator in the library; `fillna=True` remains the opt-in filling path.

**TA-3 (Medium, correctness) - ADX +DI and -DI never report their first defined bar.** `ta/trend.py:828` and `ta/trend.py:849` loop `for i in range(1, len(self._trs) - 1)`, skipping index 0, so the seed sums computed at `ta/trend.py:731,748,760` are never consumed. Measured against the StockCharts reference the project itself ships as `test/data/cs-adx.csv`: at row 14, the first bar with a published value, `+DI14` should be **6.749419** and the library returns **0.000000**; `-DI14` should be **32.419561** and returns **0.000000**. Exactly one row per series; every other row already matched. Issue #314, whose reporter had to write the missing `.head()` assertions himself. Scored Medium rather than High because the wrong value lands inside the run of zeros the warm-up already emits, so it reads as one more padding row rather than as a tradable reading, and a caller who slices off warm-up loses nothing. **How fixed**: `range(len(self._trs) - 1)` at both sites.

**TA-4 (Medium, error handling) - too-short input dies inside numpy.** `ADXIndicator` and `AverageTrueRange` size numpy buffers from `window` without checking the input. 27 bars into `adx(window=14)` raises `IndexError: index 14 is out of bounds for axis 0 with size 14` (`ta/trend.py:807`); 10 bars raises `ValueError: negative dimensions are not allowed` (`ta/trend.py:730`); 13 bars into `average_true_range(window=14)` raises `IndexError: index 13 is out of bounds for axis 0 with size 13` (`ta/volatility.py:50`). None of the three names the indicator, the parameter, or the input length - a caller batching indicators across a universe where one ticker is newly listed gets a numpy traceback and no clue. Enumerated by sweeping all 80 public indicator functions at every input length from 1 to 59: exactly 4 functions in 2 classes fail. **How fixed**: `IndicatorMixin._check_length` in `ta/utils.py`; `ADXIndicator._run` requires `window + 1`, `ADXIndicator.adx()` requires `2 * window` (the tighter bound belongs only to `adx()`, so `+DI`/`-DI` stay available above `window + 1`), `AverageTrueRange._run` requires `window`.

**TA-5 (Low, documentation) - the Bollinger `ddof` lead did not reproduce as a bug.** Issue #307 states that `ddof=0` at `ta/volatility.py:96` "is not the standard calculation". Measured against the project's own StockCharts worked example in `test/data/cs-bbands.csv`, which publishes a `20-day Standard Deviation` column: `ddof=0` reproduces it to a max error of **4.893e-07**, `ddof=1` misses by **5.824e-02**, and the library's own `bollinger_hband()` matches the published `HighBand` to 4.940e-07. Adopting `ddof=1` would widen every band half-width by `sqrt(20/19)` = **2.5978 percent** at the default window and break that reference. The library is right and the issue is wrong. What is genuinely missing is that the docstring never said so, and that the choice silently diverges from `pandas.Series.std()`'s default, which is exactly what prompted the report. **How fixed**: documented the convention and its `sqrt(n/(n-1))` consequence in the `BollingerBands` docstring, and pinned both directions with a test against the reference file so the question stops recurring.

**TA-6 (Low, code quality) - `psar_down_indicator` is derived from the up series.** `ta/trend.py:1086` reads `self._psar_up.where(self._psar_down.notnull() & ...)`. Measured, it produces no wrong output: `_psar_up` and `_psar_down` are disjoint by construction (0 rows non-null in both over 400 bars), so the expression yields NaN exactly where the down condition holds, and the following `indicator.where(indicator == 0, 1)` maps that NaN to 1. Correct by accident, one refactor away from not being. **How fixed**: read `_psar_down`; output is byte-identical and a test now pins it.

**TA-7 (Medium, testing) - the suite is structurally incapable of seeing either High.** All 32 fixtures are built by `pd.read_csv(path, sep=",")` with no `index_col`, so every test runs on a default RangeIndex: `index_col`, `set_index` and `DatetimeIndex` appear zero times anywhere under `test/`, though the README's own quickstart produces a non-RangeIndex frame. 134 lines assert on `.tail(`; zero assert on `.head(`, which is why a head-of-series defect like TA-3 survived three years after being reported. KST, the indicator carrying TA-2, has no test at all - the string "kst" appears zero times under `test/`. And two of the suite's own tests error at HEAD on any pandas >= 2.0: `TypeError: assert_series_equal() got an unexpected keyword argument 'check_less_precise'` at `test/unit/momentum.py:338` and `:348`, reproduced on both pandas 2.2.3 and 3.0.5, so `python -m unittest discover` at HEAD is **134 tests, 2 errors**. **How fixed**: `check_less_precise=True` replaced with `rtol=1e-3`; new `test/unit/invariants.py` adds two sweeps that enumerate all 80 public indicator functions rather than sampling them - one asserting index-agnosticism across DatetimeIndex, gapped-integer and reversed-integer indexes, one asserting that row k never changes when rows after k are appended - plus targeted regressions for TA-3, TA-4, TA-5 and TA-6. Suite goes from 134 tests with 2 errors to **147 tests, 0 errors** on both pandas 2.2.3 and 3.0.5; statement coverage 98 to 99 percent, missed statements 28 to 7.

**TA-8 (Medium, security hygiene) - a Coveralls repo token is committed in cleartext.** `.circleci/config.yml` exports `COVERALLS_REPO_TOKEN=ec4rvBLjmegWPIejLkGXntb92iyWF7tnR` in its "Publish coverage" step, introduced in `d124f40` on 2023-10-29 and still present at HEAD in a public repository. The token was not exercised. The blast radius is coverage reporting, not code: anyone reading the repo can post fabricated coverage for the project, and the README's third line is a Coveralls badge that would display it. Scored on that consequence, not on effort to fix. **How fixed**: removed from the file; the step now reads it from the CircleCI project environment, with a comment saying why.

**TA-9 (Medium, testing) - CI is not absent, it is red.** The premise this audit was handed was "zero CI, ever". Half of that holds: GitHub Actions has never existed here - `gh api repos/bukosabino/ta/actions/workflows` and `.../actions/runs` both return `total_count: 0`. But CircleCI is wired up and it is failing. On HEAD `a890410`, the commit-status API reports overall state `failure` with three statuses, all `failure`, all timestamped 2026-03-18: `ci/circleci: test_py36`, `ci/circleci: doc`, `ci/circleci: coverage`. The very first line of the README is a CircleCI build badge. The config targets `circleci/python:3.6` legacy convenience images and runs `isort --check-only --recursive`, a flag isort deprecated in 5.0 and now ignores with a warning. The CircleCI build logs are not publicly readable, so the cause of the red is not established here - only the state. **Not fixed**: choosing the supported Python and pandas matrix is the maintainer's call, so this went to Proposed rather than being seized.

## Classes, enumerated

The two Highs are each one instance of an idiom, so both were closed at the boundary with a full site listing rather than patched where they hurt.

*Positional loop counter used as a pandas label.* 43 integer-subscript sites appear inside indicator loops. 39 subscript numpy arrays (`self._kama` at `ta/momentum.py:342-348`; `self._trs`, `self._dip`, `self._din` at `ta/trend.py:735-767` and `:829-854`; `dip`, `din`, `directional_index`, `adx_series` at `ta/trend.py:781-811`; `atr` at `ta/volatility.py:52`) and are positional by construction. Four subscript a pandas Series by label. Three of those - `diff_directional_movement[self._window + i]`, `pos[...]`, `neg[...]` at `ta/trend.py:738,756,768` - are safe only because an explicit `reset_index(drop=True)` two lines above each one (`:732`, `:750`, `:762`) makes label equal position; they are correct and were left alone. The fourth is `ta/trend.py:1030`, the bug. Two further sites use `.iloc` on a Series correctly (`self._nvi` at `ta/volume.py:335,337`). The boundary fix moves the whole PSAR recursion off pandas, and `TestIndicatorsAreIndexAgnostic` now re-derives the enumeration mechanically over all 80 public functions on every run, so a new site cannot be added silently.

*Whole-series aggregate used as a warm-up `fill_value`.* 14 sites, all in `ta/trend.py`: TRIX at `:273-274`, Ichimoku at `:414` and `:432`, KST at `:500,502,511,513,522,524,533,535`, DPO at `:600`, Vortex at `:896`. Measured per site, 8 leak - the KST ones, reaching `kst()` and `kst_sig()`. The other 6 are latent, not harmless: each is masked only by a NaN that happens to sit downstream (TRIX's `ewm` warm-up, Vortex's `vmp`/`vmm` shift, DPO's rolling mean, and Ichimoku's, which is inert only because `visual` defaults to False - set it True and the leak is live). All 14 removed. `TestIndicatorsDoNotLookAhead` enumerates the same 80 functions and fails on any future site.

*Standard-deviation convention.* Exactly one `ddof` in the library, `ta/volatility.py:96`. Verified correct, documented, tested. Settled.

## Verification

`fixes.patch` applies cleanly to a pristine checkout of `a890410710a6e483c9ba08da7f3dd5089e4b9dff`. After applying it there:

- `python -m unittest discover`: **147 tests, OK** on pandas 3.0.5 and on pandas 2.2.3 (was 134 tests, 2 errors on both).
- `python repro.py --repo <checkout>`: **12 checks, 12 passed**. At unpatched HEAD the same script is 10 failed on pandas 3.0.5 and 8 failed on pandas 2.2.3 - the two that flip are the DatetimeIndex PSAR checks, which is the pandas 3 regression stated in TA-1.
- Behaviour audit: all 80 public indicator functions computed at HEAD and after the patch on identical input. **76 are bit-identical.** The 4 that change are exactly the 4 findings: `adx_pos` and `adx_neg` at row 14, `kst` at rows 14-43, `kst_sig` at rows 14-51. No indicator changed that this report does not name.
- `black --target-version py36 --check` and `isort --check-only` clean; `pycodestyle --max-line-length=119` reports only pre-existing E203 (black's slice-colon style, as at HEAD).

Diffstat: 7 files, +424/-82, of which `test/unit/invariants.py` is 311 new lines of test.

**Routed to the owner under Proposed, not seized**:
1. **The CI matrix.** All three CircleCI jobs are red at HEAD against `circleci/python:3.6` images, and the README advertises the badge. Whether to repair CircleCI or move to GitHub Actions, and which Python and pandas versions to support, is a maintainer decision, not an auditor's.
2. **The pin gap that caused TA-1 to go silent.** `requirements-core.txt` pins `numpy==1.21.5` and `pandas==1.3.5` while `setup.py` declares unpinned `numpy` and `pandas`. Every real install gets pandas 2.x or 3.x; the only tested configuration is a pandas the library never ships against. Reconciling the two is an owner decision about the supported range.
3. **KST's warm-up becomes NaN.** TA-2's fix removes 30 rows that previously carried numbers. They were wrong numbers, but anyone consuming rows 14-43 sees a change, so this belongs in a release note.
4. **`ADXIndicator.adx()` now raises below `2 * window` rows** instead of throwing `IndexError` from numpy. Correct, and also observable.

**Disclosed limitation**: the CircleCI build logs for the failing runs are not publicly readable, so TA-9 states the red state, which was observed through the GitHub commit-status API, and explicitly does not claim a cause. The Coveralls token in TA-8 was never exercised; that finding rests on a credential sitting in a public repository, not on demonstrated abuse. The two 80-function sweeps run each indicator at its default parameters on one synthetic price path with one truncation point - they are an exhaustive enumeration of *sites*, not of parameter space, so a defect that appears only at a non-default `window` would not be caught. No indicator was cross-checked against a third-party implementation; TA-3 and TA-5's external correctness claims rest on the StockCharts reference CSVs the project itself ships and tests against. `docs/`, `examples_to_use/` and the bundled notebook were not audited. The Bollinger conclusion is that `ddof=0` matches StockCharts and the project's own fixture; it is not a claim about every charting package a user might compare against.

**Independently verified**: the red-green cycle was re-run from a clean clone at `a8904107` on Python 3.13 with pandas 3.0.5. The upstream suite at HEAD is `Ran 134 tests ... FAILED (errors=2)`; `repro.py` grades 2 of 12 checks passing. After `git apply fixes.patch` the suite is `Ran 147 tests ... OK` and the repro is 12 of 12. Note for anyone repeating this: the project's test files are not named `test_*`, so pytest collects nothing and reports "no tests ran"; use `python -m unittest discover -s test -p '*.py'`.

**Status**: fixes live in this eval's artifacts; nothing was pushed upstream. Upstream disclosure pending review.
