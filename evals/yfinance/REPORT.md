# Jeffy audit: ranaroussi/yfinance (price repair)

**Target**: [ranaroussi/yfinance](https://github.com/ranaroussi/yfinance) (24,812 stars, verified `gh api repos/ranaroussi/yfinance --jq .stargazers_count` on 2026-07-27) at HEAD `beac22d981ab37362a70c9e4e49261ac622acbe4`, 2026-07-23, "Version 1.5.2". Python 3.13.8, pandas 3.0.5, numpy 2.5.1, scipy 1.18.0 - audited in a local clone under Jeffy's method; nothing was pushed upstream, no issue or PR was opened.

**Scope**: the price-repair module, `yfinance/scrapers/history.py`, reached by `Ticker.history(repair=True)` and `download(repair=True)`. The envelope is the one the module writes itself into: its input is Yahoo's chart JSON, third-party content the library does not control, and the module exists because that content is known to be wrong in specific ways - pence/pound mixups, missing dividend adjustments, unapplied splits, zeroed prices. Yahoo-shaped bad data is therefore in envelope, not an exotic malformed input. What is out of envelope is hand-mangled frames Yahoo would never emit; nothing below relies on one.

**The headline**: the repair module has four in-envelope defects that produce wrong prices or a hard crash, plus a class defect in the `Repaired?` contract. The most severe is not the one the leads pointed at. A GBp-quoted instrument whose table also contains a genuine 100x block error comes back with **every row 100x too big and the repair flag inverted** - 90 of 90 rows wrong in the reproduction, the 20 genuinely broken rows reported clean and 40 clean rows reported repaired. Separately, yfinance's **own golden fixture** `tests/data/SSNLF-1d-bad-div.csv`, added by the maintainer for the "Adj Close went to infinity" case, raises `ValueError: assignment destination is read-only` at HEAD on pandas 3.

Reproduction is entirely offline. `repro.py` blocks `socket.connect`, `socket.create_connection` and `socket.getaddrinfo` before the first case runs and drives the repair functions with seeded fixture frames, so a case that silently reached Yahoo would raise rather than pass. Every number below was observed.

| Case | Severity | Behaviour at HEAD (unpatched) |
|---|---|---|
| Y1 | High (correctness / error handling) | `ValueError: assignment destination is read-only` on any frame with `inf` in `Adj Close` |
| Y2 | High (correctness) | GBp table + genuine 100x block: 90/90 rows returned 100x too big, flag inverted |
| Y3 | High (correctness) | Crude 100x fallback leaves `Adj Close` bad; default `auto_adjust` reapplies the 100x to every column |
| Y7 | High (correctness / error handling) | `ZeroDivisionError` on a fund that paid capital gains with no dividend that day |
| Y4 | Medium (correctness) | Crude fallback collapses the bar to its body: true range 1.0875% -> 0.0635% of Close |
| Y5 / Y9 | Medium (correctness / silent failure) | Two price-mutating paths never write `Repaired?`; the docs promise it |
| Y6 | Medium (observability) | The only INFO report of a crude repair can never fire - its counter reads a pre-tag snapshot |
| Y8 | Medium (error handling / observability) | The pence/pound assumption is applied unchecked and unannounced for any window older than 30 days |

**Found and fixed**:

- **Y1 (High, correctness / error handling)** - `_fix_bad_div_adjust` writes into a read-only numpy view. `history.py:1642` takes `adjClose = df2['Adj Close'].to_numpy()`, then writes into it at `history.py:1647`; under pandas copy-on-write that array is not writable. Reproduced offline: `ValueError: assignment destination is read-only`, the exact traceback and the exact line number in issue [#2890](https://github.com/ranaroussi/yfinance/issues/2890). Nothing in `history()` catches it - the only `try` there wraps `auto_adjust` at `history.py:499-512` - so `Ticker.history(repair=True)` fails outright rather than returning data. The strongest evidence is upstream's own: replaying `tests/data/SSNLF-1d-bad-div.csv`, the fixture the maintainer added for "Adj Close went to infinity", raises this at HEAD and matches its `-fixed` golden after the patch. The same file already applies the identical defensive copy for the same idiom at `history.py:2802-2803`, so the hazard is known; this site was missed. Fixed by taking an owned copy, `to_numpy(copy=True)`.

- **Y2 (High, correctness)** - the unit-switch double-correction guard rescales the whole table after a partial repair, and inverts every flag. `history.py:1098` sets `self._history_metadata["currencyRepaired"] = True` unconditionally, including when the subunit check decided *not* to convert. `history.py:3377-3392` then reads that flag: if any repaired block had `m < 1`, it multiplies **every** row of `Open, High, Low, Close, Adj Close` by 100 and flips the flag array with `sudden_change_repaired = ~sudden_change_repaired` at `history.py:3392`. That is only correct when the repair covered the entire table - the double of `_standardise_currency`'s whole-table conversion. When Yahoo has a genuine 100x block inside an otherwise correct pence table, the branch fires anyway. Reproduced offline on a 90-row GBp fixture with a 20-row block error: **90 of 90 rows come back 100x too big** (`Close[0] = 5000.85` against a true 50.01), the 20 broken rows report `Repaired? = False` and the 40 untouched rows before the block report `True`. With the branch skipped, the same fixture repairs perfectly: 0 of 90 wrong. Fixed at both ends - `currencyRepaired` is set only when a conversion actually happened, and the revert is gated on `sudden_change_repaired.all()`.

- **Y3 (High, correctness)** - the crude 100x fallback rescales prices but not `Adj Close`, and the default adjustment path then reapplies the error. When `_reconstruct_intervals_batch` cannot reach finer data - which is every 1d row older than Yahoo's ~730-day intraday window, so every historical backtest - `history.py:1244-1289` rescales `Open` and `Close` by 0.01 and never touches `Adj Close`. The still-tagged `Adj Close` is restored to its original bad value by the "restore original values where repair failed" loop at `history.py:1304-1310`. `utils.auto_adjust()` (`utils.py:497-514`), on by default, then multiplies `Open/High/Low` by `Adj Close / Close` and renames `Adj Close` to `Close`. Reproduced offline on a row whose true values are `O=47.9880 H=48.0945 L=47.5730 C=47.9575`: after `repair=True` plus the default `auto_adjust`, yfinance returns `O=4798.7973 (x100.0) C=4795.7502 (x100.0)`. The unrepaired row was at least internally consistent; the repaired one is still 100x wrong and reports `Repaired? = False`. Fixed by including `Adj Close` in the crude rescale.

- **Y7 (High, correctness / error handling)** - `_repair_capital_gains` divides by an empty count. `history.py:1542` computes `pct_double_counted = sum(dcs.values()) / len(dcs)`, but `dcs` only gains an entry for a capital-gains row that has a preceding interval *and* passes the `dividend < capital_gains` filter at `history.py:1518-1520`. A fund that distributes capital gains with no dividend on that date - ordinary behaviour - populates nothing, and so does a frame whose only capital-gains row is the first row. Reproduced offline in both shapes: `ZeroDivisionError: division by zero`. `_repair_capital_gains` is called unguarded at `history.py:494`, so this kills `Ticker.history(repair=True)` for the affected fund. Fixed by treating an empty `dcs` as "nothing assessable, nothing to repair" instead of dividing.

- **Y4 (Medium, correctness)** - the crude fallback throws away `High` and `Low` it can recover exactly. `history.py:1259-1267` (and the reciprocal branch at `1281-1289`) overwrites them with `max`/`min` of the already-fixed `Open, Close`, even though both were flagged as the same 100x error and are therefore recoverable by the same division. Reproduced offline: true `High=48.0945, Low=47.5730`, bar range 1.0875% of Close; yfinance returns `High=47.9880, Low=47.9575`, range 0.0635% - the bar collapsed to its body, which corrupts every range-based estimator downstream (ATR, Parkinson, Garman-Klass). This is the reproducible repair-module core adjacent to issue [#2857](https://github.com/ranaroussi/yfinance/issues/2857). Fixed by rescaling `High`/`Low` by the detected factor and clamping only enough to keep a partially repaired row self-consistent.

- **Y5 + Y9 (Medium, correctness / silent failure)** - `Repaired?` reports `False` on rows the module rewrote. `doc/source/advanced/price_repair.rst:7` states the column "specifies if row was repaired", and line 18 documents exactly one exception, the Adj-Close-only dividend fix. Two price-mutating paths violate that. (a) `_standardise_currency` at `history.py:1094-1096` multiplies every price column by 0.01 for `GBp`/`ZAc`/`ILA` with no flag write anywhere in the function. Reproduced on the real XDEV.L pence values printed in issue [#2866](https://github.com/ranaroussi/yfinance/issues/2866): `Close 6272.0 -> 62.72`, `Repaired?` column not even created - matching the reporter's output. (b) The crude 100x fallback at `history.py:1254-1289` rewrites `Open, Close, High, Low` and never writes the flag either; the only flag write in that region is inside `_reconstruct_intervals_batch` at `history.py:1052`, which by construction did not run on that path. Reproduced: prices rewritten, `Repaired? = False`. Fixed at both sites.

  Enumeration backing the class claim: every site in `history.py` that assigns to a price, `Adj Close`, `Dividends` or `Volume` column was listed and checked. Sites that already set the flag correctly: `_reconstruct_intervals_batch` 1034-1052, `_fix_bad_div_adjust` 1676-1680 / 1714-1715 / 1725-1726 and the dividend corrections at 2021-2626, `_repair_capital_gains` 1558-1572 (flag at 1565), `_fix_prices_sudden_change` 3271-3352 / 3386-3391 (flag at 3396). The only two price-mutating sites that did not are the two fixed above. Two dividend-only sites also do not - see Proposed.

- **Y6 (Medium, observability)** - the only user-visible report of a crude repair can never fire. `history.py:1217` snapshots `df2_data = df2[data_cols].to_numpy()`, the tags are written afterwards at `history.py:1237`, and `history.py:1239` then counts them in the stale snapshot: `n_before = (df2_data == tag).sum()`, always 0. `n_fixed = n_before - n_after_crude` at `history.py:1296` is therefore never positive and the `logger.info(f"fixed {n_fixed}/{n_before} currency unit mixups ...")` at `history.py:1298-1302` never emits. Reproduced by capturing the yfinance logger at INFO while a repair demonstrably happened: 0 such lines. The sibling function `_fix_zeroes` does the same thing in the right order at `history.py:1437-1438`, which is what identifies this as an ordering slip rather than intent. Fixed by counting after tagging. Combined with Y5 this meant a crude 100x repair left no trace at all - not in the data flag, not in the log.

- **Y8 (Medium, error handling / observability)** - the pence/pound assumption is applied without ever being tested, silently. `history.py:1082` hardcodes `prices_in_subunits = True` and the only thing that can clear it is a live-quote ratio check at `history.py:1083-1093`. That check is skipped entirely whenever the newest row is more than 30 days old (`history.py:1083`) - so for essentially every historical window - and when `regularMarketPrice` is absent from metadata the resulting `KeyError` is swallowed by `except Exception: ... pass` at `history.py:1089-1093`, leaving the assumption in force. Reproduced offline on a GBp-tagged frame Yahoo had already served in pounds, window ending 400 days ago: correct prices of `62.7200` are divided again to `0.6272`, with no warning and no flag. Fixed by replacing the bare except with explicit checks and logging a `WARNING` naming exactly why the assumption could not be verified. The guess itself was **not** changed - see Disclosed limitation.

**What did not reproduce, and what the leads got wrong**:

- **Issue [#2866](https://github.com/ranaroussi/yfinance/issues/2866) is right about one of its three claims.** The pence-to-pounds conversion is not a bug: `doc/source/advanced/price_repair.rst:9` says repair "can also repair currency mixups, so check `Ticker.history_metadata['currency']` after for true currency", and the reproduction confirms `history_metadata['currency']` is updated `GBp -> GBP` alongside the division. Recorded as `DOCUMENTED-2866a`. The complaint that "volumes have not been adjusted" is also wrong - a currency conversion must not rescale a share count, and leaving `Volume` alone is correct. Recorded as `NOTREPRO-2866b`, asserted so the fix cannot regress it. The third claim, `Repaired?` reporting `False` after every price in the table changed, is real and is Y9. So the lead's framing - a 100x price error that silently corrupts correct data - does not hold as a data-corruption finding; what holds is a contract violation in the flag. The genuine 100x corruption in this module is elsewhere, in Y2 and Y3.

- **Issue [#2857](https://github.com/ranaroussi/yfinance/issues/2857) as filed is a feature request, not a repair-module defect.** It reports raw Yahoo rows where `High < max(Open, Close)` and asks repair to clip them. No repair function claims to enforce OHLC ordering, and the reproduction confirms the violation survives `_fix_unit_random_mixups` and `_fix_zeroes` untouched. Recorded as `NOTREPRO-2857`, informational. What the issue does point at, indirectly, is Y4: the one place the repair module *does* rewrite `High`/`Low` is the place it destroys information it already has.

- Differential regression over yfinance's own golden fixtures. Unpatched: 41 match their goldens, 1 raises (`SSNLF`, Y1). Patched: **42 of 42 match**, and every digest except `SSNLF` is byte-identical to the unpatched run. The patch fixes upstream's own broken fixture and changes nothing else.
- `pyflakes` clean on the patched file. Diffstat: 2 files, +98/-61.

**Routed to the owner under Proposed, not seized**:

- **Two dividend-only mutation sites that do not set `Repaired?`**: `history.py:2547` (`df2.loc[dt, 'Dividends'] /= currency_divide`) and `history.py:2571` (`*= currency_divide`), both in the "Adj Close is correct, just need to fix Dividend" branches. These are the third and fourth instances of the Y5 class, and under this method the third instance ends instance work. They are also a genuine contract question rather than an obvious slip: `price_repair.rst:18` already carves an Adj-Close-only fix out of the flag, so whether a dividend-only fix counts as "row repaired" is the maintainer's call, not the auditor's. Filed, not patched.
- **The `prices_in_subunits = True` default itself.** Y8 makes the guess loud and flagged but leaves it a guess. Deciding whether Yahoo more often serves GBp-tagged tables in pence or in pounds needs live measurement across LSE/JSE/TASE tickers. That is the owner's data to gather.
- **Issue 2857's actual request** - clipping every raw `High`/`Low` to the candle body across all data. That is new repair behaviour that would silently rewrite Yahoo data on rows nothing flagged, with a false-positive profile the maintainer would have to accept. Out of scope for a defect fix.
- **An offline fixture tier for the repair tests.** `tests/test_price_repair.py` wraps every CSV replay in `yf.Ticker(...)` purely to obtain a timezone string, which forces the whole suite onto the live, rate-limited API even for the parts that are pure golden-file comparisons. The differential harness written for this audit shows the same 42 fixtures run offline in seconds. Proposing the split, not imposing it.

**Disclosed limitation**: the upstream test suite hits live Yahoo endpoints and is rate-limited, so it was never run, and no finding here was checked against a live ticker. Everything is driven by hand-built fixture frames and by yfinance's own committed CSV fixtures, offline and seeded. Three consequences, stated rather than papered over. First, the reproductions establish that each code path does what is claimed, not how often the real world enters it - Y2 needs a GBp/ZAc/ILA ticker whose table also contains a partial 100x block, and Y8 needs Yahoo to serve major units under a subunit tag; the module's own guard is the maintainer's evidence that the second state occurs, and the `AET.L` and `SSW.JO` block fixtures are his evidence for the first, but neither frequency was measured here. Second, the specific tickers in the issues - `XDEV.L`, `ENV.CR`, `AAPL` - were not fetched; the XDEV.L fixture is transcribed from the values the reporter printed in the issue, and the infinity case uses upstream's own `SSNLF` fixture instead of `ENV.CR`. Third, Y1's crash is pandas-version dependent, verified in both directions: it fails on pandas 3.0.5 and on pandas 2.3.3 with `copy_on_write` enabled, and passes on pandas 2.3.3 with the old default. yfinance declares `pandas>=1.3.0` (`setup.py:62`), so a fresh install today lands on pandas 3 and hits it.

**Independently verified**: the red-green cycle was re-run from a clean clone at `beac22d9` on Python 3.13, pandas 3.0.5, numpy 2.5.1, scipy 1.18.0. Unpatched, `repro.py` grades 3 of 16 cases passing; after `git apply fixes.patch`, 16 of 16. Reproduction note for anyone repeating this: `scipy` is an optional yfinance dependency that `pip install -e .` does not pull in, and without it six cases abort inside `_fix_unit_random_mixups` at `history.py:1218` rather than grading, which understates the failure count in both directions.
