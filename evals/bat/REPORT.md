## What the loop found

- **T1 (High, security)** - `--sanitize=always`, the feature upstream merged to defuse escape-sequence and Unicode-spoofing attacks, was **completely inert whenever stdout is piped**: `bat --sanitize=always evil.txt | cat -v` reproduced the raw ESC and CR bytes verbatim, because the loop-through path's SimplePrinter never called the sanitizer at all. That is exactly the context sanitization exists for - piping untrusted content onward. Fixed inside SimplePrinter, deliberately scoped to `--sanitize` alone, because an upstream test pins `--strip-ansi`'s loop-through passthrough as intended design; that asymmetry is filed as a Proposed item for upstream's contract call, not resolved unilaterally.
- **T3 (High, correctness)** - the T1 fix itself, one iteration old: `String::from_utf8_lossy` on raw UTF-16 bytes turned every UTF-16 file piped under `--sanitize=always` into U+FFFD soup. The iteration 4 audit found it, and the journal owns it in writing: *"a regression I introduced."* Fixed by decoding `ContentType::UTF_16LE/BE` exactly as the interactive printer does, plus stripping a line-1 UTF-8 BOM - a second latent defect (BOM replaced by U+FFFD instead of removed) found and fixed inside the same task.
- **T2 (Medium, correctness)** - `sanitize` substituted 9 of the 12 Unicode `Bidi_Control` codepoints while the help text promised bidi coverage generally: U+200E, U+200F and U+061C passed straight through. Settled as a class, not three patches - the new test iterates the full 12-codepoint set and names any missing member, and a second test proves the widened 0xD8 trigger byte does not eat ordinary Arabic text that shares it.
- **T4 (Medium, error handling)** - a typo in `--language` was silently ignored whenever color was off: `bat -l nosuchlang --color=never` exited 0 and printed the file, while the identical command with color exited 1 with a clear message. Validation now runs in the controller before any pager spawns, with `-A`'s internal pseudo-language deliberately accepted and pinned by test.

The closing audit swept the last five inventory rows with known-answer probes (mock pagers that name themselves to prove three-way precedence, identical file content under three different identities to prove syntax detection keys on identity), scored every dimension over all 15 rows, and entered closeout with zero High and zero Medium in-envelope. The evaluator PASSed on first invocation - and earned its keep not by rejecting but by reach: its independent probes (truncated multibyte at EOF, a lone 0xD8 lead byte, 8-bit C1 CSI, binary input, files without trailing newlines) covered byte-level edges the run's own acceptance checks had not.

The Stop hook then rejected **two** convergence declarations in a row: first a Converged line written as a markdown list item the hook's column-anchored parser could not see, then a parenthetical annotation on the plan's Command line, which the hook executes verbatim as shell (exit 2). bat makes it **four projects in a row** whose first declaration died on a machine-read line written for a human reader. Both repairs were verified against the hook's own parser expressions, on a code tree that never changed after the certified commit.

## Honest caveats

- `--sanitize` is unreleased: no tag contains the baseline commit, so T1 never reached release users. The loop found the hole in the window between merge and release - which is also the window in which an upstream fix is cheapest.
- One inventory row's bookkeeping lagged its evidence: the sanitize-feature row was not flipped back after iteration 5 changed `transform_untrusted`, code that row covers. The overlapping printer-core and input rows were re-swept at that same commit with the UTF-16 probes, and the evaluator's independent attack hit exactly that surface at the converged tree - the coverage is real, the row's recorded commit is not current. Stated here rather than papered over.
- LESSOPEN support is behind a non-default cargo feature and absent from this build; `src/lessopen.rs` was not exercised by any probe, and the journal says so in the same words.
- The post-run review noted three deliberate behavior deltas, each defensible and none pinned by any prior test: binary content under `--sanitize=always` is now lossily decoded rather than passed raw (raw passthrough would be a sanitize bypass); an unknown `--language` now errors once to stderr before the pager spawns instead of per-input into the pager stream; and loop-through invocations carrying a valid `-l` now load the syntax set they previously never touched.
- The run converged on its final budgeted iteration - ten of ten - on the third declaration attempt. Every machine-checked condition was verified at that tree and re-verified fresh for this receipt.
