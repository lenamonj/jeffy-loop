# Jeffy eval: shopspring/decimal

**Target**: [shopspring/decimal](https://github.com/shopspring/decimal) (7,457 stars, verified via `gh api`) at HEAD `3090cc487febd78d6016c2859c66308328a40e99` (2026-06-29), Go 1.26.2 - audited in a local clone; nothing was pushed upstream.

This is the arbitrary-precision decimal type most Go payment and ledger code depends on, and its rounding methods are the primitives those systems use to produce the amounts they settle and store. The last release, v1.4.0, is `a1bdfc355e9c71119322b748c95f7d6b82566e30` dated 2024-04-12; seven commits have landed on `master` in the 27 months since, none of them touching the rounding family. `go test ./...` is green at HEAD (`ok github.com/shopspring/decimal 5.982s`, 115 top-level tests, 0 failures). The audit ran the seven referenced open issues to ground, then audited the rounding family as a class against exact `big.Rat` arithmetic: 240,000 randomised value comparisons across `Round`, `RoundUp`, `RoundDown`, `RoundCeil`, `RoundFloor` and `RoundBank`, plus 19,877 across `DivRound`, found **zero wrong values**. Every defect found is in the *scale* of the result, not its magnitude.

**Found and fixed**:

- **D1 (Medium, correctness) - the rounding family does not agree on the scale of its result** - `decimal.go:1579` and `1584-1586` (`RoundCeil`), `1604` and `1609-1611` (`RoundFloor`), `1629` and `1634-1636` (`RoundUp`), `1656` and `1661-1663` (`RoundDown`). Each of the four directional rounders has two early-return paths that hand back the *input* decimal rather than one rescaled to `-places`, so the scale of the result depends on the data rather than on the argument. `Round` and `RoundBank` return exponent `-places` in 20,000 of 20,000 randomised cases; the four directional rounders return something else in 6,482 of the same 20,000 (32.4%). Reproduced consequence, exact values: `RequireFromString("100.0").Round(0)` returns exponent `0` while `.RoundUp(0)` returns exponent `-1` (issue [#390](https://github.com/shopspring/decimal/issues/390), open since 2024-12-27). With `TrimTrailingZeros = false` - the mode the library itself documents as "useful for APIs where exact decimal string representation matters" - two ledger amounts pushed through the *same* `RoundUp(2)` call come out at different scales: `"10.500"` marshals to JSON as `"10.500"` and yields `driver.Value` `10.500`, while `"10.501"` marshals to `"10.51"` and yields `10.51`. The numeric value is correct in both; the column precision written to the database is not. Fixed by aligning all four on the contract `Round` already keeps - `if d.exp == -places { return d }`, and return the rescaled decimal rather than `d` when rounding is a no-op - which also let `RoundDown` collapse to a bare `d.rescale(-places)`, since truncation toward zero *is* round-down. That this is the intended family contract is corroborated inside the library: `StringFixed(3)` on `5.45` produces `"5.450"` only because `Round(3)` pads to `-places`. No internal caller uses the four methods (enumerated: the only in-repo `.Round*` call sites on `Decimal` are `StringFixed`->`Round`, `StringFixedBank`->`RoundBank`, `StringFixedCash`->`RoundCash`, `RoundBank`->`Round`, `RoundCash`->`Round`, and `Round` inside `ExpTaylor`/`ExpHullAbrham`/`Ln`; the `Round`/`RoundUp`/`RoundDown` in `rounding.go` and `decimal-go.go` are methods on the unexported `decimal` shortest-float helper, not on `Decimal`). **This changes observable output; the adoption decision is routed under Proposed below.**

- **D2 (Medium, correctness) - `RoundCash` silently follows the global `DivisionPrecision`** - `decimal.go:1731`, `return d.Mul(dVal).Round(0).Div(dVal).Truncate(2)`. `Div` is `DivRound(d2, DivisionPrecision)`, and `DivisionPrecision` is an exported package variable the library's own doc comment demonstrates reassigning. Any caller who sets it below 2 gets a silently wrong cash amount from a function whose own doc comment promises "5: 5 cent rounding 3.43 => 3.45". Reproduced consequence, exact values: with `DivisionPrecision = 1`, `RequireFromString("3.43").RoundCash(5)` returns `3.5` instead of `3.45` (and `-3.43` returns `-3.5` instead of `-3.45`); with `DivisionPrecision = 0` it returns `3`, and `RequireFromString("3.45").RoundCash(10)` returns `4` instead of `3.5` while `"3.41".RoundCash(25)` returns `4` instead of `3.5`. Fixed by pinning the division precision at the function's own scale: `d.Mul(dVal).Round(0).DivRound(dVal, 2)`. The quotient is exact at 2 decimal places for all five supported intervals (the multipliers are 1, 2, 4, 10, 20), which also makes the trailing `Truncate(2)` a provable no-op, so it was dropped. Verified non-breaking at default settings: 100,000 randomised inputs x 5 intervals compared against the pre-fix expression at `DivisionPrecision` of 2, 3, 4, 8, 16 and 30 - **600,000 comparisons, 0 differences in value or exponent**. Scored Medium rather than High because the default configuration is unaffected; the wrong amount requires a caller to have set `DivisionPrecision` below 2.

**Leads that did not reproduce, or that are documented conventions rather than defects** (each is a passing assertion in `repro_test.go`, so the claim is checkable):

- **[#385](https://github.com/shopspring/decimal/issues/385) "calling DivRound on a negative number returns a positive number" - not reproduced.** `NewFromFloat(-35.0).Div(NewFromFloat(5.0))` returns `-7` at HEAD and at v1.4.0. 19,877 randomised `DivRound` comparisons against exact rational half-away-from-zero rounding, across mixed signs and precisions from -2 to 9, produced 0 mismatches. The issue's snippet does not compile as written (`DivRound` takes two arguments), which is the likely source of the report.
- **[#375](https://github.com/shopspring/decimal/issues/375) "RoundUp() and RoundDown() with Negative Numbers" - reproduced, but documented, not a defect.** `RoundUp` documents itself as "rounds the decimal away from zero" and carries `NewFromFloat(-1.454).RoundUp(1).String() // output: "-1.5"` in its own doc comment; `RoundDown` documents "towards zero" with the matching `-1.4`. Both behave exactly as documented. `RoundCeil` and `RoundFloor` provide the towards-+/-infinity semantics the reporter expected, and do so correctly.
- **[#388](https://github.com/shopspring/decimal/issues/388) "RoundUp can round a number that shouldn't be rounded" - not reproduced.** `RequireFromString("3.692").Mul(RequireFromString("1.25"))` is exactly `4.615` carried as coefficient `461500` at exponent `-5`, and `.RoundUp(3)` returns `4.615`, not the reported `4.616`, at HEAD and at v1.4.0. The guard that makes this correct (`if d.Equal(rescaled)`) was added in commit `99f4d74c` on 2021-01-18 and shipped in every release since, so the report cannot be against a released version at or after v1.3.0.
- **[#394](https://github.com/shopspring/decimal/issues/394) / [#380](https://github.com/shopspring/decimal/issues/380) `Pow` with negative exponents - reproduced exactly, but documented.** `NewFromInt(10).Pow(NewFromInt(-18))` returns `0`; so does `-17`; `-16` returns `0.0000000000000001`. `Pow`'s doc comment states the result "will have maximum precision of PowPrecisionNegativeExponent places after decimal point", and that variable's documented default is 16, so a value needing 17 or more places underflows the fixed scale to exactly zero. Both documented escape hatches work: `PowWithPrecision(NewFromInt(-18), 20)` returns `0.000000000000000001`, and setting `PowPrecisionNegativeExponent = 18` makes `Pow` return it too. Painful for 18-decimal crypto amounts, and a real v1.3.1-to-v1.4.0 behaviour regression, but it is the documented contract - the remedy is a maintainer decision, filed under Proposed rather than padded into a defect.
- **[#411](https://github.com/shopspring/decimal/issues/411) "NewFromFloat loses precision on integers" - reproduced exactly, but documented.** `NewFromFloat(float64(5202671607238904832))` returns `5202671607238905000`. `NewFromFloat`'s doc comment states it keeps "the number of significant digits that can be represented in a float with reliable roundtrip... typically 15 digits", and `5202671607238905000` does round-trip to the same float64. `NewFromFloatWithExponent(f, 0)` returns the exact `5202671607238904832`, and the doc comment already points callers there for absolute precision.

**Nothing among these leads was fixed-in-main-but-unreleased.** The identical probe was run against the v1.4.0 tag in a second worktree and produced byte-identical output to HEAD on all seven leads. The story is the reverse of the expected one: the rounding family has not been touched since before the last release, and the one lead that genuinely does not reproduce (#388) was already correct when it was filed.

**Routed to the owner under Proposed, not seized**:

1. **Adopting D1 is a breaking change to observable output, and that call is the maintainer's.** After the fix, `RoundUp`/`RoundDown`/`RoundCeil`/`RoundFloor` always return exponent `-places`, which changes `Exponent()`, changes `String()` whenever `TrimTrailingZeros = false`, changes `String()` for negative `places` whenever `UseScientificNotation = true`, and pads with trailing zeros when `places` exceeds the input's scale (`RequireFromString("1").RoundUp(2)` now has exponent `-2`, matching `Round(2)`). The full upstream suite passes unchanged, so no in-repo behaviour depends on the old scale, but downstream golden-file and string-equality tests may. A narrower variant exists if the maintainer wants to fix #390 without the padding: keep the `if d.exp >= -places { return d }` fast path and change only the `d.Equal(rescaled)` branch to `return rescaled`. That fixes the reported case and removes the data-dependent scale for all inputs finer than `places`, while leaving the four methods still divergent from `Round` for inputs coarser than `places`. The patch here implements the full alignment because it closes the class at its boundary; the narrower variant is the conservative option.
2. **Whether `Pow` should stop underflowing to zero (#394, #380).** Any of: raise the default `PowPrecisionNegativeExponent`, scale the precision to the magnitude of the exponent, or keep the cap and document the underflow at the `PowPrecisionNegativeExponent` declaration. Not seized - it is a deliberate v1.4 design decision with a stated rationale, and changing it changes results for every existing caller.
3. **`Pow` returns the zero-value `Decimal` both as its documented sentinel for undefined cases (0\*\*0, 0\*\*negative, negative base with fractional exponent) and as the genuine value of an underflowed result.** A caller cannot tell "undefined" from "underflowed to zero". Low severity, doc-only remedy available, but it is an API ambiguity the maintainer should settle rather than an auditor.

**Disclosed limitation**: the audit covered the rounding family (`Round`, `RoundUp`, `RoundDown`, `RoundCeil`, `RoundFloor`, `RoundBank`, `RoundCash`, `DivRound`, `Truncate`, `Floor`, `Ceil`) and the seven named leads. The JSON/SQL/Spanner codecs, `NewFromString` parsing, and the `Ln`/`Exp`/trigonometric routines were exercised only incidentally by the full upstream suite and were not audited. The D1 fix gives the four directional rounders the same large-`places` allocation profile `Round` already has: `RequireFromString("1").RoundUp(100000)` now allocates a 100,001-digit coefficient, measured at 1.85ms against `Round`'s 1.28ms - the same cost class, but a path those four methods did not previously have. Star count is 7,457 at the time of audit, not exactly the ~7.5k in the brief.

**Independently verified**: the red-green cycle was re-run from a clean clone at `3090cc48` on Go 1.26.2. The upstream suite is green before any change (`ok github.com/shopspring/decimal 12.130s`).
