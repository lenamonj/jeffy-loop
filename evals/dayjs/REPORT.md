# Jeffy eval: iamkun/dayjs

**Target**: [iamkun/dayjs](https://github.com/iamkun/dayjs) (48,655 stars, verified 2026-07-27 with `gh api repos/iamkun/dayjs`) at HEAD `98364bcebc047529345cc8c2bbcc44a6a8c18e79` on branch `dev`, committed 2026-06-30 19:46:40 +0800, latest release v1.11.21 (2026-05-26), 63,006,037 npm downloads in the week 2026-07-18 to 2026-07-24. Node v22.18.0, Windows 11. This is an audit conducted under Jeffy's method, not a loop run. Everything ran in a local clone; nothing was pushed upstream.

**The lead that started this audit was wrong, and establishing that was the first real result.** The brief said the suite fails at HEAD under the project's own CI timezone, with `dayjs('2015-01-01T00:00:00.000Z').dayOfYear(4).toISOString()` returning `2014-01-05T00:00:00.000Z` instead of `2015-01-04T00:00:00.000Z`, the wrong year. That failure is real, it is not a Windows artifact, and it is not a defect in dayjs. It is a timezone-fragile test fixture, and it does not occur under Pacific/Auckland at all.

Two things had to be untangled before anything could be trusted. The first was a harness artifact: under Git Bash, `TZ=Europe/London node ...` never reaches the process, because MSYS2 strips a `TZ` value containing a slash. Only `TZ=UTC` survives. Every "different timezone" run made that way silently executes in the machine's own zone, which here is America/New_York. That is what produced the earlier report of a dayOfYear failure under Pacific/Auckland: the process was never in Auckland. Driving the runs through the project's own `cross-env` instead makes the variable arrive, and the picture changes completely. `repro.js` now refuses to run at all unless it can first prove that changing `TZ` actually changes the process clock.

The second was the finding itself. `dayjs('2015-01-01T00:00:00.000Z')` is 2014-12-31 local in any zone west of Greenwich, so `dayOfYear()` correctly returns 365, and setting it to 4 correctly lands on 2014-01-04 local. **moment returns exactly the same value**, character for character, on the same host. The library is right and the fixture is wrong.

**The headline is a different bug entirely, and the search for it is what the audit was actually for.** `dayjs.tz()`, whose entire purpose is to be independent of the machine it runs on, returns different answers on different machines, and on some machines returns an object whose `format()` and its own `valueOf()` describe instants an hour apart. Separately, `dayjs.tz()` resolves an ambiguous or skipped local time by asking what the target zone's offset is at the moment the code runs, so the same call returns a different instant in January than it does in July. Both reproduce on host UTC or on host Europe/London, both are ordinary arithmetic rather than anything platform specific, and both are fixed here.

## Findings

**DAYJS-1 (High, correctness) - `dayjs.tz()` returns a different answer depending on the machine's own timezone.** `src/plugin/utc/index.js:105` shifts the instant by a fixed number of milliseconds to park the target wall clock into a native `Date`'s local fields, using the host offset read at the *pre-shift* instant. When the host zone has a DST transition inside that shift window, the offset no longer applies at the shifted instant and the stored wall clock stops describing the same moment as `valueOf()`. Separately, `src/plugin/utc/index.js:121` reads `this.$x.$localOffset || this.$d.getTimezoneOffset()`, so a legitimate stored offset of 0, which is what a host sitting at UTC+00 produces, is treated as missing and silently replaced. Reproduced: on host America/Whitehorse, `dayjs.tz('2012-03-11 02:00:00', 'America/New_York')` formats as `2012-03-11T04:00:00-04:00`, which is 08:00Z, while the same object's `toISOString()` says `2012-03-11T07:00:00.000Z`; on host Europe/London, `dayjs.tz('2012-10-28 00:30:00', 'America/New_York')` lands on `2012-10-28T05:30:00.000Z` where moment-timezone and every other host give `04:30:00.000Z`, a full hour of drift in the instant itself. Across 8 host zones the single call `dayjs.tz('2012-03-11 02:00:00', 'America/New_York')` produced 2 distinct results. This is what makes 4 tests in `test/plugin/timezone.test.js` fail under `TZ=America/Whitehorse`, one of the project's own three named CI zones. Fixed by probing the shift once and re-anchoring on the host offset that actually applies at the shifted instant, and by testing `$localOffset` for absence instead of for truthiness. After the fix the same call is identical on all 8 host zones.

**DAYJS-2 (High, correctness) - an ambiguous or skipped local time is resolved from the current date, so the same call gives different answers at different times of year.** `src/plugin/timezone/index.js:138` seeds the disambiguation guess with `tzOffset(+d(), timezone)`, the target zone's offset at the moment the code runs. Reproduced on host UTC with the clock frozen: `dayjs.tz('2021-11-07 01:30:00', 'America/New_York')` returns 1636266600000 when run in January and 1636263000000 when run in July; the `Pacific/Auckland` and `Europe/London` fall-back inputs drift the same way. Three of the four boundary inputs tested moved by exactly one hour depending only on the calendar. Fixed by seeding the guess from the parsed input instead of from `Date.now()`. The four inputs are now stable, and `2021-11-07 01:30:00 America/New_York` now also agrees with moment-timezone, which it previously did only for half the year.

**DAYJS-3 (High, correctness) - arithmetic on a timezone-bound instance never re-resolves the zone.** A Day.js instance produced by `.tz()` carries the offset captured at construction, and `add`, `subtract`, `startOf` and `endOf` all inherit it rather than asking the zone again. `src/plugin/timezone/index.js:135-148` sets `$x.$timezone` and a fixed `$offset`; `src/index.js:54` propagates `$offset` and `$x` through `Utils.w` on every derived instance. Reproduced on host UTC: `dayjs.tz('2021-03-13 23:30:00', 'America/New_York').add(1, 'day')` formats as `2021-03-14T23:30:00-05:00`, but New York is on `-04:00` that day, and moment-timezone returns `2021-03-14T23:30:00-04:00`, an hour earlier in absolute terms. Sweeping 6 operations across 14 DST-boundary timestamps in 4 target zones, 84 checks per host, produced between 22 and 37 disagreements with moment-timezone on every one of 10 host zones tried, and the count varies by host, so the derived instances are wrong and host-dependent at the same time. This is the substance of upstream issue [1260](https://github.com/iamkun/dayjs/issues/1260), open since 2020-12-07 with 39 comments. **Not fixed here.** Correcting it means the plugin must re-resolve the zone after every unit-aware operation, which is a design change to observable behavior across the whole plugin surface, not an audit patch. Routed to the owner, below.

**DAYJS-4 (Medium, testing) - five test files pin expectations that only hold in some timezones.** `test/plugin/dayOfYear.test.js:33` asserts `toISOString()` on a value derived from a local-calendar operation seeded with a `...Z` literal; `test/plugin/localizedFormat.test.js:26` uses `new Date(0)` and then asserts the year is 1970, which is false in every zone west of Greenwich; `test/get-set.test.js:103`, `test/plugin/pluralGetSet.test.js:117` and `test/plugin/calendar.test.js:23` do the same with `...Z` literals whose local calendar date moves. Reproduced: the table above. In every case the library agrees with moment exactly on the same host, which is what proves these are fixture defects and not library defects; `test/plugin/calendar.test.js` even asserts agreement with moment on the line above the one that fails. Fixed by expressing the fixtures as local wall clock literals and asserting local calendar output, which leaves what each test is checking intact. All 93 suites now pass under all 8 host zones tried.

**DAYJS-5 (Medium, testing) - the CI timezone matrix exercises 6 tests out of 773.** `package.json:9` defines `test-tz` as `jest test/timezone.test`, and `package.json:8` runs it under `Pacific/Auckland`, `Europe/London` and `America/Whitehorse` before running the full suite once with no `TZ` set. That pattern matches exactly one file, `test/timezone.test.js`, 1 suite and 6 tests, verified with `jest test/timezone.test --listTests`. Everything else, including all of `test/plugin/timezone.test.js`, runs only in the runner's default zone, which on `ubuntu-latest` is UTC. That is precisely why upstream CI is green on a commit whose full suite is red under two of the three zones CI names. Fixed by pointing `test-tz` at the whole suite; the timezone matrix now runs 93 suites per zone. This change is only safe because DAYJS-1 and DAYJS-4 are fixed with it, and it was verified in that order.

**DAYJS-6 (Medium, dependency hygiene) - the development toolchain is from 2018.** `npm audit` on a clean install reports 177 vulnerabilities, 7 low, 52 moderate, 81 high, 37 critical. `npm ls core-js` shows three copies of the deprecated `core-js@2.6.12`, reached through `babel-plugin-external-helpers > babel-runtime`, through `jest@22.4.4 > jest-cli > jest-runtime > babel-core@6 > babel-register`, and through `karma@2.0.5`. The shipped package is not affected: dayjs declares no runtime dependencies at all, so none of this reaches a consumer. The exposure is maintainer machines and CI. **Not fixed here.** Moving from jest 22 to a current jest, and from karma 2 and eslint 4, is a harness migration with its own large diff and its own risk of masking behavior changes in a library whose correctness is entirely about edge cases; doing it inside a correctness audit would make the correctness diff unreviewable. Routed to the owner, below.

## What came back clean

The core library's DST handling is sound. A matrix of 10 operations, `add(1, 'day')`, `subtract(1, 'day')`, `add(24, 'hour')`, `add(1, 'week')`, `add(1, 'month')`, `startOf('day')`, `endOf('day')` and `diff` in hours, days and minutes, run against both the spring-forward and the fall-back boundary in 5 host zones including the half-hour-DST zone Australia/Lord_Howe, produced 100 checks and **zero** disagreements with moment. Every defect found in this audit lives in the `timezone` and `utc` plugins, not in the core. `eslint` is clean at HEAD and stays clean. Line coverage is 100 percent at HEAD and remains 100 percent after the patch, so the repo's own `coverageThreshold` gate still passes.

**Routed to the owner under Proposed, not seized**:
- **DAYJS-3, re-resolving the zone after arithmetic.** Making `add`, `subtract`, `startOf` and `endOf` re-ask the zone would align dayjs with moment-timezone and close issue 1260, but it changes observable output for every caller who does arithmetic on a `.tz()` instance across a DST boundary. That is a semver-visible decision for the maintainer, not an audit patch.
- **DAYJS-6, the dev toolchain migration.** jest 22, karma 2 and eslint 4 to current, which is what clears the 177 audit findings and the three deprecated core-js copies. It touches no shipped code and belongs in its own change.
- **Which occurrence an ambiguous local time should resolve to.** The DAYJS-2 fix makes the answer deterministic, which it was not before. It does not settle the convention: dayjs now resolves `2021-04-04 02:30:00` in `Pacific/Auckland` to `+12:00` and `2021-10-31 01:30:00` in `Europe/London` to `+00:00`, the later of the two occurrences, where moment-timezone and Luxon both pick the earlier. Matching them is a deliberate contract choice and is left to the owner. Before the fix dayjs matched moment for roughly half the year and disagreed for the other half, which is worse than either convention.
- **The `patches/` directory and the 2.99 KB `size-limit` budget.** Untouched. Any fix that grows `dayjs.min.js` has to be weighed against a budget the owner set; the change here does not touch core, so it does not consume it.
- **Upstream issue 1227, the default-timezone constructor.** Read and left alone. It is a feature request about `dayjs.tz.setDefault` not applying to the plain constructor, open since 2020-11-16 with 42 comments, not a defect against current documented behavior. Filing an audit finding against it would be inventing a contract the project has not made.

**Disclosed limitation**: every result here was produced on Windows 11 with Node v22.18.0 (win32) and the ICU data bundled with that build. **What was ruled out**: that the failures are Windows timezone-data artifacts. Windows ICU's history for the zones used matches the published tzdata rules exactly, checked directly: America/Whitehorse reads 01:59 PST at 2012-03-11T09:59:00Z and 03:00 PDT one minute later, and permanent UTC-7 from 2020 onward after Yukon stopped observing DST; Europe/London reads GMT throughout the same window. More decisively, DAYJS-2 reproduces on host UTC, where no zone history is involved at all, and DAYJS-1 reproduces on host Europe/London, whose rules are as unambiguous as any zone's. The mechanism in both cases is arithmetic in the library over offsets the platform reports correctly, which is why the reasoning carries to Linux and macOS. Also ruled out: the Git Bash `TZ` passthrough artifact described at the top, which invalidated an earlier pass of this audit and is now guarded against in `repro.js`.

**What was not ruled out**: I did not execute anything on Linux or macOS, so the claim that these reproduce there is reasoning from the mechanism and from a correct platform tz database, not an observation. The upstream CI evidence is consistent with that reasoning but does not test it, because DAYJS-5 means CI never runs the affected suites outside UTC. A maintainer should confirm on `ubuntu-latest` with `TZ=America/Whitehorse` and `TZ=Europe/London` before treating the Linux behavior as established. Separately, the timezone-fragile fixtures in DAYJS-4 were reproduced on 7 host zones, not exhaustively; other zones may surface further fixtures, and the fix addresses the ones observed. Finally, `npm run lint` as written (`./node_modules/.bin/eslint ...`) cannot execute on Windows cmd, so lint was verified by invoking `eslint` directly with the same arguments; that is a limitation of this audit harness, not a project defect, since CI runs on Linux.

**Independently verified**: the red-green cycle was re-run from a clean clone at `98364bce` on Node 22.18.0. `repro.js` scores 1 of 5 at HEAD and 5 of 5 after `git apply fixes.patch` and a rebuild, with DAYJS-4 passing in both directions, which is the assertion that proves the reported "wrong year" was never a library defect. Two traps for anyone repeating this: `npm run build` fails on Node 22 with `error:0308010C digital envelope routines::unsupported` unless `NODE_OPTIONS=--openssl-legacy-provider` is set, and the build writes `dayjs.min.js` to the clone root rather than a `dayjs/` subdirectory, so pass the clone path to the repro as `node repro.js <clone-root>`.
