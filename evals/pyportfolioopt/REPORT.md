# Jeffy eval: PyPortfolio/PyPortfolioOpt

**Target**: [PyPortfolio/PyPortfolioOpt](https://github.com/PyPortfolio/PyPortfolioOpt) (5,894 stars, verified via `gh api`) at HEAD `a6638d2e06dae6f444fd022cfd4b3c528902a85b` (2026-07-07), Python 3.13.8 with numpy 2.5.1, scipy 1.18.0, cvxpy 1.9.2, pandas 3.0.5 - audited in a local clone; nothing was pushed upstream.

This is the library people use to turn a price history into position sizes. Its outputs are weights that get traded, so the ranking that matters here is: a silently wrong weight is worse than a crash, and a crash with a useless message is worse than a clear error. The audit ran the three referenced issues to ground, then audited input validation across `EfficientFrontier`, `CLA` and the risk-model helpers as one class - 40 (entry point, degenerate input) pairs, each classified as fail-clearly, fail-raw, warn-and-return, or return-silently. At HEAD that class scored **1 clear error, 8 raw library exceptions, 6 warn-and-return and 25 silent returns**; after the patch, **10 / 2 / 10 / 18**.

**Baseline first**: the project's own `Test` workflow run [28899115146](https://github.com/PyPortfolio/PyPortfolioOpt/actions/runs/28899115146) is RED at exactly this commit (`head_sha` `a6638d2e...`, verified via `gh api`), reporting `5 failed, 280 passed, 32 skipped` with every failure `AttributeError: module 'scipy.cluster.hierarchy' has no attribute '_LINKAGE_METHODS'`. Reproduced locally at the same HEAD with all extras installed: **7 failed, 305 passed, 5 skipped** - the same five plus two `test_plotting` tests that CI skips because its coverage job installs no matplotlib. All seven share one root cause. It is not environmental: `scipy==1.17.0` still exposes `_LINKAGE_METHODS`, `scipy==1.18.0` (released 2026-06-19) does not, and `pyproject.toml` declares `scipy>=1.3.0` with no upper bound, so a fresh install resolves the broken combination. The 1.6.0 wheel on PyPI carries the same line at `pypfopt/hierarchical_portfolio.py:152`.

## Found and fixed

- **PPO-1 (High, correctness) - `HRPOpt.optimize()` is dead on any current scipy** - `pypfopt/hierarchical_portfolio.py:179`, `if linkage_method not in sch._LINKAGE_METHODS:`. The guard reads a private scipy attribute that moved out of the `scipy.cluster.hierarchy` namespace in scipy 1.18 (it now lives in `scipy.cluster.hierarchy._hierarchy_impl`). Reproduced consequence: every call to the documented public method raises `AttributeError`, including the default `linkage_method="single"` - the entire Hierarchical Risk Parity feature is unreachable, and this is what turns the project's own default branch red. Fixed by deleting the pre-check: `scipy.cluster.hierarchy.linkage` validates the method itself and raises `ValueError: Invalid method: <name>` before touching data, so the documented `ValueError` contract and the existing `test_hrp_errors` assertion both survive without any private-API dependency.

- **PPO-2 (High, correctness) - `CLA` builds turning points that violate the budget constraint, and `max_sharpe` then silently returns a suboptimal portfolio** - `pypfopt/cla.py:201`, `wB = self._reduce_matrix(self.w[-1], b, [0])`. `_get_matrices` slices the bounded weights out of `self.w[-1]`, the *previous* turning point. But at `cla.py:381` the solve loop has already written the boundary value into the live weight vector for the asset that just became bounded, so `wB` carries a stale interior value for exactly that asset and the free weights are solved against the wrong bounded budget. Reproduced consequence, 300 synthetic positive-definite problems (2 to 6 assets, distinct expected returns, nothing degenerate): **50 of 300 produce at least one turning point whose weights do not sum to 1, worst `|sum(w)-1| = 9.073e-01`**. `_purge_num_err` correctly deletes those points, after which `max_sharpe` interpolates between survivors that are no longer adjacent on the frontier - the chord cuts the corner. **22 of 300 problems return a portfolio more than 0.01 percent below the true optimum, worst 2.0156 percent of Sharpe ratio**, with no warning of any kind. cvxpy is the oracle and scipy SLSQP agreed with it independently to 10 significant figures on the worst case. Fixed by passing the live weight vector into `_get_matrices` rather than re-reading `self.w[-1]`. After: **0 of 300 off-budget turning points (worst `2.132e-14`, machine precision) and 0 of 300 shortfalls**. The change is provably a no-op at the other three call sites, where the live vector and `self.w[-1]` are elementwise equal.

- **PPO-3 (High, correctness) - equal expected returns produce a raw exception or, worse, a wrong portfolio** - `pypfopt/cla.py:176` returns `(None, None)` when `_compute_lambda`'s denominator `c` is exactly zero, which identical expected returns guarantee, and `cla.py:367-368` compares that raw `None`. Reproduced consequence over 300 synthetic equal-return problems: **244 raise `TypeError: '>' not supported between instances of 'NoneType' and 'float'`, 1 raises `IndexError: list index out of range` from `_purge_excess` at `cla.py:271`, and 55 return a portfolio - of which 31 are strictly worse than the true optimum, worst a 76.2 percent Sharpe shortfall**. Minimal case: `mu = [0.1, 0.1]`, `S = [[0.04, 0.01], [0.01, 0.04]]` returns `[0.0, 1.0]` (Sharpe 0.500000) when the optimum is `[0.5, 0.5]` (Sharpe 0.632456), a 20.9 percent shortfall. This is a bug and not a documented precondition, and the proof is continuity: at `mu = [0.1, 0.1 + 1e-10]` the same code returns `[0.5, 0.5]` exactly. The answer is discontinuous only at exact equality. Fixed by detecting the degeneracy in `_solve` and raising a `ValueError` that names it and points at `EfficientFrontier(...).min_volatility()`, which remains well defined. `_purge_excess` also got a `len(self.w) < 2` guard for the `IndexError`, and the abandoned commented-out perturbation hack at `cla.py:72-73` was deleted now that a real guard exists.

  **The obvious fix here is the wrong fix, and that is recorded rather than asserted.** Issue 738's diagnosis implies guarding the raw `lam` with `_infnone`. Applying only that, on the same 300 problems, makes the `TypeError` go away and turns **294 of 300 into returned answers of which 256 are silently suboptimal, worst 85.8 percent of Sharpe**. It converts 245 loud crashes into 256 silent wrong answers. `repro.py` item `N2` runs that variant and asserts the outcome, so the claim is checkable.

- **PPO-4 (High, correctness) - `CovarianceShrinkage` silently records a missing return as a 0 percent return** - `pypfopt/risk_models.py:532`, `556`, `613`, `666`, all `X = np.nan_to_num(self.X.values)`. numpy and sklearn have no notion of a missing return, so an asset that was not yet listed reads as an asset that did not move, and its variance is diluted in proportion to how much history is missing. `self.S` on the same object uses pandas' pairwise deletion, so the two disagree on the same input. Reproduced consequence on **the project's own shipped test fixture** (`tests/resources/stock_prices.csv`, 20 tickers, 7126 rows, of which 6230 have at least one NaN because the tickers list at different dates): `ledoit_wolf` puts BABA's annualised variance at **0.01344** against `sample_cov`'s **0.10096**, an 86.7 percent understatement that tracks BABA's 87.4 percent missing history almost exactly (FB -78.7 percent at 79.2 percent missing, GM -73.0 percent at 73.9 percent, GOOG -51.2 percent at 51.8 percent; GE and XOM, with complete histories, agree to 0.4 and 0.9 percent). The estimator therefore reports BABA as the lowest-variance asset in the universe, and `EfficientFrontier(mu, ledoit_wolf).min_volatility()` puts **43.2 percent of the portfolio in BABA against 12.6 percent from `sample_cov` on the identical prices** - a 30.7 percentage-point difference in the largest position, produced entirely by the fill. Nothing warns. **Fixed only to the extent of ending the silence**: the constructor now warns, naming the count of missing returns and the disagreement with `self.S`. The numbers are deliberately left unchanged - see Proposed below.

- **PPO-5 (Medium, error handling) - singular positive semidefinite covariance crashes with a raw numpy exception** (issue [#737](https://github.com/PyPortfolio/PyPortfolioOpt/issues/737)) - `pypfopt/cla.py:342`, `357`, `374`, `386`, all unguarded `np.linalg.inv(covarF)`. Perfectly collinear assets give a covariance matrix that is a mathematically valid PSD input but is singular. Reproduced consequence: `CLA(mu, S).max_sharpe()`, `min_volatility()` and `efficient_frontier()` all raise `numpy.linalg.LinAlgError: Singular matrix` from a private helper, naming neither the input nor a remedy. Fixed at the class boundary rather than per site: one `_invert` helper carries all four inversions and converts the `LinAlgError` into a `ValueError` naming collinearity and listing the three remedies (drop the redundant assets, shrink the covariance, or use `EfficientFrontier`, which does not need an invertible matrix).

- **PPO-6 (Medium, error handling) - a NaN in the covariance reaches the weights** - `pypfopt/cla.py:71-75`, which performed no numeric validation at all. Reproduced consequence: a covariance matrix with one NaN entry - what a price history with a gap or a zero price produces - yields the portfolio `{0: 0.0, 1: nan, 2: 0.0}` with zero warnings, and `clean_weights()` preserves the NaN rather than hiding it. `EfficientFrontier` rejects the same input, so `CLA` was the only entry point that did not. Fixed with a single `np.isfinite` boundary in `__init__` covering both `expected_returns` and `cov_matrix`.

- **PPO-7 (Medium, error handling) - cvxpy's raw `SolverError` escapes carrying a bare status code** - `pypfopt/base/_base_optimizer.py:339`, `except (TypeError, cp.DCPError) as e:`. `cp.SolverError` is not in the tuple. Reproduced consequence: `EfficientFrontier(mu, S).min_volatility()` on a negative-definite matrix raises `cvxpy.SolverError: 4` - the entire message is the solver's status integer. That the input is invalid is a documented precondition; that the message is a bare `4` is not a precondition, it is an unhelpful failure. Fixed by adding `cp.SolverError` to the tuple already in place, so it becomes the library's own `OptimizationError` with the original preserved as `__cause__`.

## Leads that did not reproduce

- **`CLA` is not non-deterministic** (the claim in issue [#738](https://github.com/PyPortfolio/PyPortfolioOpt/issues/738)'s title). Identical input run 20 times in-process across 20 random problems gives 1 distinct outcome; the same programme run under `PYTHONHASHSEED` of 0, 1, 12345 and 99 gives 1 distinct result set. The suspected mechanism - `_diff_lists` returning `list(set(...) - set(...))`, whose iteration order would be a hash-order dependency - does not bite, because the elements are small integers whose CPython hash is the integer itself. The issue's *other* claim, the `TypeError`, reproduces exactly and is PPO-3. `repro.py` items `N1` and `N1b` assert non-reproduction, so the negative claim is checkable rather than asserted.

- **Ill-conditioned covariance produces no wrong result to warn about** (issue [#694](https://github.com/PyPortfolio/PyPortfolioOpt/issues/694)). Confirmed absent: nothing in `risk_models` or either optimizer inspects the condition number. But on a PSD matrix with condition number 1.0e+12 both `EfficientFrontier.min_volatility()` and `CLA.max_sharpe()` returned the corner solution the matrix actually implies, not garbage. It is a missing diagnostic, not a defect, and it is filed upstream as an enhancement rather than a bug. Not fixed - the warning threshold is a judgement call, routed under Proposed.

## The degenerate-input class, enumerated

40 (entry point, degenerate input) pairs across `CLA`, `EfficientFrontier` and the risk-model helpers, run before and after the patch. Rows that changed:

| Entry point | Degenerate input | At HEAD | After |
|---|---|---|---|
| `CLA.max_sharpe` / `min_volatility` / `efficient_frontier` | singular PSD covariance | raw `LinAlgError: Singular matrix` | clear `ValueError` |
| `CLA.max_sharpe` / `min_volatility` | equal expected returns | raw `TypeError` or silently wrong weights | clear `ValueError` |
| `CLA.max_sharpe` | NaN in covariance | silent `{0: 0.0, 1: nan, 2: 0.0}` | clear `ValueError` |
| `EF.min_volatility` / `max_sharpe` | negative-definite covariance | raw `cvxpy.SolverError: 4` | `pypfopt.OptimizationError` |
| `EF.min_volatility` | indefinite covariance | raw `cvxpy.SolverError: 4` | `pypfopt.OptimizationError` |
| `CovarianceShrinkage.*` (4 estimators) | NaNs in the price history | silent, variance diluted by the missing fraction | warns, naming the count and the disagreement |

Rows deliberately left alone, because they are right or are documented preconditions honoured loudly: a single asset returns `{A: 1.0}` from both optimizers; `EfficientFrontier` on a singular PSD covariance returns a valid optimum, since it never inverts anything; `fix_nonpositive_semidefinite` on a negative-definite matrix returns the zero matrix with a warning, which is exactly what projecting onto the PSD cone means when every eigenvalue is negative; `sample_cov` on a two-row price history returns all-NaN with numpy's own divide-by-zero warnings; `cov_to_corr` on a zero-variance asset returns NaN correlations with numpy's warnings. `CLA` on a negative-definite or indefinite matrix still returns weights silently - that gap is real but the remedy is a design decision, routed below.

**Routed to the owner under Proposed, not seized**:

1. **The NaN convention for the shrinkage estimators (PPO-4).** The patch makes the dilution visible; it does not change a single number. There is no clearly-right minimal fix. Listwise deletion was implemented first and rejected on evidence: it discards 6230 of 7126 rows of the project's own fixture, and it broke seven upstream tests. Pairwise deletion is what `self.S` already does but cannot be fed to `sklearn.covariance.ledoit_wolf`, which takes a data matrix. Handling staggered listing histories properly inside a shrinkage estimator is a modelling decision with published alternatives, and it belongs to the maintainer, not to an auditor.
2. **Whether `CLA` should route through `np.linalg.pinv` instead of erroring on a singular covariance**, as issue 737 also proposes. The error was chosen because a singular covariance makes the optimum genuinely non-unique, and `pinv` would silently return one arbitrary member of that set - the exact failure mode this envelope ranks worst. The maintainer may weigh convenience differently.
3. **Whether `CLA` should reject or warn on a non-PSD covariance.** It currently returns weights silently where `EfficientFrontier` fails loudly. `risk_models._is_positive_semidefinite` already exists and a constructor check is three lines, but it would reject inputs that today produce output, so it is a behaviour change for the owner to take.
4. **An ill-conditioning warning (issue 694)**, including where the condition-number threshold should sit.
5. **An upper bound on `scipy` in `pyproject.toml`.** PPO-1 shipped to users because `scipy>=1.3.0` is unbounded. The fix removes the dependency on the private attribute so no bound is needed for this bug, but the general policy is the maintainer's call.

**Disclosed limitation**: the suite was already red at HEAD and this report does not claim otherwise. Exact before-and-after, both measured on a `git worktree` pinned at `a6638d2e...` in a separate virtualenv, `MPLBACKEND=Agg`, `python -m pytest ./tests`:

- **Before**: `7 failed, 305 passed, 5 skipped` - `test_hrp.py::{test_hrp_errors, test_hrp_portfolio, test_portfolio_performance, test_pass_cov_matrix, test_quasi_dag}` and `test_plotting.py::{test_dendrogram_plot, test_weight_plot}`, all `AttributeError: module 'scipy.cluster.hierarchy' has no attribute '_LINKAGE_METHODS'`.
- **After**: `312 passed, 5 skipped, 0 failed`.

Two further disclosures. Without `MPLBACKEND=Agg` this Windows box adds two `_tkinter.TclError` failures in `test_plotting`; those are environmental, are excluded from both counts above, and CI forces the same backend. It now filters by category before counting, which is what the assertion always meant. That is the only test change in the patch; no test was deleted, skipped or weakened.
