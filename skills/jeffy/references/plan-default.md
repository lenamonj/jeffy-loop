# Plan

## Mode

## Goal
Raise this project to the standard a top-tier engineer would sign off on: correct on edge cases, secure by default, tested where failure hurts, simple to change, honest in its docs. Audit dimensions: architecture, code quality, security, testing, error handling, performance, documentation, dependency hygiene, developer experience, correctness, observability, and, where a user-facing surface exists, UX and accessibility. Ordering principles: correctness and security outrank polish, simplicity outranks cleverness, deleting code beats adding it, and improvement is measured by user and maintainer impact, never by activity. Leave the project materially better on every pass.

## Operating envelope
Severity is judged against this envelope, never against imagined callers. Before filing any finding, the first audit enumerates every input surface - network endpoints, CLI arguments, environment, config files, data files, state files the project writes and reads back - and classifies each with one trust class, recorded in the table below. Later audits re-read the table and must not reclassify it.

Trust classes:
- adversarial: untrusted parties can reach it (public endpoints, uploads, third-party content). The full severity rubric applies, including hostile hand-crafted input.
- user-error: the project owner hand-authors it (CLI flags, config, seed data). A wrong value deserves a clear failure message; findings about exotic malformed shapes beyond that are Low at most.
- machine-generated: the project's own pipeline produces it. The generator's real output is the contract; hand-mangled or off-contract variants are out of envelope, Low at most, Declined by default.
- state-at-rest: the project writes it and reads it back. External corruption of it is out of envelope, Low at most.

Surfaces (first audit fills this in, one line each):
- <surface>: <trust class> - <one-line reason>

Binding rules:
- A finding exercised only by out-of-envelope input is Low at most, whatever its consequence.
- Only the user widens the envelope or reclassifies a surface. An audit that believes the envelope is wrong files one Proposed item and moves on; it never files the finding at rubric severity.
- Where robustness to malformed input on a surface is genuinely wanted, the remedy is one structural task - a single validation boundary where that input enters - never scattered per-site guards.

## Surface inventory
The audit's map, and the run's bound. Before filing any finding, the first audit enumerates the project's whole public surface - every public module, class group, entry point, or command a user can reach - as one checkbox row each, listed completely before any row is explored in depth. Enumerate from the code, not from the documentation: every source file belongs to some row, including underscore-private modules that implement public behavior, because dead or orphaned code that no entry point reaches is exactly what a call-path sweep never visits. Size rows so one checkbox certifies a comparable amount of surface: a module with dozens of public functions gets several rows split by function family, never one, or the rows-swept count overweights trivial rows and a single checkbox quietly stands for half the project. A row starts unswept: `- [ ] <surface>: <scope>`. An executed probe, and only an executed probe, flips it: `- [x] <surface>: swept at <commit> - <what the sweep exercised>`. A row whose implementing code changes after its recorded commit is stale: flip it back to unswept, because the old sweep no longer certifies the new code. A third state exists for surface this host cannot reach at all - a platform-only build, a service that cannot be installed here: `- [~] <surface>: unreachable on this host - <reason>`. It is a disclosure, not a sweep. Convergence requires no unswept `- [ ]` row, every `- [~]` row is named with its reason in the run report, and a later run on a host where the reason no longer holds flips it back to `- [ ]` and sweeps it.

For a surface that computes values, a probe is a correctness check, not a liveness check. Sweeping such a row requires at least one known-answer test per function family it covers - a closed form, a hand-computed small case, or an independent reference implementation - or a strong invariant that a wrong result would break. Run-without-crashing flips nothing there: the costliest defects return wrong numbers without complaint, and a crash-biased sweep files every type error while certifying wrong arithmetic as clean. A metric off by a constant factor, a parameter silently ignored, and an aggregation that quietly no-ops all pass a liveness probe and all fail a known-answer one. A row's known-answer battery is kept, not rebuilt: write it under `.jeffy/probes/<row-slug>` so the iteration checkpoints commit it, and a re-sweep re-runs that battery instead of reconstructing the instrument, which is where most re-sweep cost goes. A battery is updated in the same iteration as the behavior it pins, so it never certifies a contract the code no longer has. A battery may declare the paths it covers in `.jeffy/probes/<row-slug>/paths`, one glob per line relative to the project root; an iteration whose diff touches a declared path runs that battery in the same iteration and treats a failure exactly as it treats a Verify failure, because a check outside the Verify command is a check that runs when someone remembers - a six-iteration-old regression once sat green behind every verify gate while the battery that owned it waited for the close. A battery with no paths file keeps the closeout-only behaviour, so existing projects degrade gracefully.

A sweep also exercises every documented parameter of the functions it certifies, at two or more values that must change the output, including the negative or boundary side of the domain where one exists. A documented parameter whose value changes nothing is a finding, never a pass, unless the documentation itself says it should have no effect in that case. This is a recurring class, not a corner: an inert flag, a rate applied only when positive, and an aggregation token falling through to no-op are the same defect wearing three names, and a sweep that probes a parameter only where it works will certify the row while the parameter is dead everywhere else.

Dimension scores claim only swept rows. A None on a dimension whose surface still has unswept rows is silence, not cleanliness, and an audit that presents such a score as the whole project is the failure this table exists to prevent: a library scored correctness None across five audits while an entire simulation module sat unexamined, and every audit's new High was simply the next unvisited room. The first audit therefore probes breadth-first - every row shallowly before any row deeply - so the worst defect in the project appears in the first filing, not the sixth.

Convergence requires that this table lists no unswept row, and the Stop hook checks that mechanically. That is what makes the loop bounded: the surface is finite, sweeps only accumulate, and the remaining work is always the visible remainder of a written list rather than a hope that the next audit comes back empty. The run report states progress as rows swept of rows total. These rows are scheduled work with a bound, not audit incidentals: the loop's queue orders open High tasks, then unswept or stale Surface inventory rows, then open Medium tasks, then open Low tasks, so the map outranks everything but an open High and neither a Medium nor a Low can starve the sweep; a sweep iteration batches every row it can properly evidence with the evidence bar per row unchanged, the Stop hook projects when the map clears from the run's own observed sweep rate and says so every iteration, and a run whose projection says the map cannot clear inside the budget is ended early with that arithmetic rather than at exhaustion. Closeout ends the hunt for new findings on swept surface, never the mapping of unswept surface: sweeping continues in closeout, and a High or Medium a closeout sweep surfaces is filed and worked exactly as one the closing audit filed.

Rows (first audit fills this in, one line each):
- [ ] <surface>: <scope>

## Verify command
One runnable command that must exit 0 for this project to count as unbroken - the test suite, the build, or a validator script. The first audit fills this in; write none with a one-line reason only if the project genuinely has no runnable gate. It runs at the end of every iteration: a failure the previous checkpoint did not have means the iteration broke the project, and the iteration is reverted.

An exit status is a narrow thing to trust, so the same first audit writes down what that status actually covers. `Oracle class` names what the command grades, in your own words: unit tests, a conformance corpus, a differential comparison against a reference implementation, a build only. `Environment fingerprint` names the platform, the toolchain versions, and every test target this platform excludes - and that exclusion list is derived by a command, enumerating the build constraints, platform guards and skip markers in the test tree, with the line naming the command that produced it. Never a bare assertion that nothing is excluded: the whole failure this exists to catch is an exclusion nobody looked for. The declaring iteration re-reads both lines, and a test asset the fingerprint says the command cannot reach is one no journal entry may claim was green. A run once converged over 29 iterations while its project's 402-case conformance corpus never executed at all - the only file importing it carried a build tag for another platform, and the command's own package selection never reached it - and that run asserted twice that the corpus was passing. Nothing mechanical could catch it, because the command exited 0 every time; only the declaration could have.

The gate is run through `skills/jeffy/hooks/lib/quiet-verify.sh`, never as the raw command, and the reason is context rather than convenience: a green suite prints its whole passing output into the window every iteration, in a session where context already accumulates - the engine's own validator is 226 lines of `OK` on a green run. Through the wrapper a green run prints nothing to stdout and one line to stderr; a red run prints its last `Verify output budget` lines, default 80; a timeout is a failure. Silence must not cost the record, though, because journal entries and receipts quote real verify counts: `Verify summary pattern` names a regex, and the single line of output matching it rides the green line so the figure stays quotable. The wrapper also refuses a `PLAN.md` whose `Oracle class` is declared-but-empty or half-migrated, which the converged stop refuses anyway - the difference is that the run finds out at its second iteration instead of at its declaration.

A suite whose runtime is worth recording gets one more labeled line. `Verify duration: <N>s measured <date>` states the suite's wall time from a real timed run, and the Stop hook derives its converged-stop bound from it, resolving `verify_timeout_seconds`, else `Verify duration` x3 floored at 240s, else 240s, so a legitimately slow suite is not refused at the declaration for outrunning a bound nobody measured; the launcher reads the same line so a relaunch inherits the bound. Record it when a timed run shows the suite near or past four minutes, and update it in the same iteration as any change that moves the measurement materially.

Command: <first audit fills this in>
Oracle class: <first audit fills this in>
Environment fingerprint: <first audit fills this in>
Verify duration: <optional; from a timed run, when the suite runs near or past four minutes>
Verify output budget: <optional; lines of failing output the wrapper prints, default 80>
Verify summary pattern: <optional; regex matching the one result line worth quoting, e.g. [0-9]+ (passed|OK)>

## Method
Audit the project against every applicable dimension and score each by its highest finding severity: High, Medium, Low, or None. Skip dimensions that do not apply and record why. Every audit consults the Surface inventory first and sweeps unswept or stale rows before re-probing swept ones; an audit never wanders. When replenishing with a partial audit, target the dimensions least recently scored and the inventory rows least recently swept.

Severity rubric - judge by consequence, not by effort to fix:
- High: users get wrong results, data loss or corruption, a security vulnerability, a crash on realistic in-envelope input, or a broken build or install.
- Medium: failure on a plausible in-envelope edge case, a silently swallowed error, missing tests on a path whose failure would matter, misleading documentation, or a dependency with a known vulnerability.
- Low: polish - naming, style, minor docs, cosmetic gaps.

Evidence rule: a finding exists only if you can point at it - a file and line, a failing command, or a reproduced behavior. Verify before filing; no speculative findings. File the root cause, not each symptom.

Publication rule: code that leaves this project - an issue body, a pull request description, a report, a message to anyone - must be run in exactly the form it is published, and its stated output must be that run's real output. Trimming a working script down to something shorter and clearer does not inherit the original's verification: a reduction is new code, and it is unverified until it has been executed as written. Verifying one artifact and shipping a different one is the failure this rule exists to stop, and it is expensive, because the person who finds the broken version is the person whose trust was being asked for.

Write findings into BACKLOG.md as prioritized checkable tasks, worst severity first: High in Now, Medium in Next, Low in Later; break ties by user impact, then by smallest effort. Each line names its class: `- [ ] <ID> (<Severity>, <class>, <dimension>): <finding>. Acceptance: <check>.` - class is one of runtime, test, build-ci, docs, dev-tooling, chosen by the files the fix will touch, and a legacy line without one is read as runtime. Order within a section by severity first, then runtime before the other classes, because shipped behavior is what a user meets and perimeter work is what a run drifts into. Every task must be completable in a single iteration - split it if not - and must carry an acceptance check that is a runnable command or an observable fact, never an opinion. An acceptance check must be strong enough to fail: run it against the unfixed code and confirm that it does, because a check the broken implementation also satisfies proves nothing. Prefer a differential or invariant assertion over an absence-of-badness one - a sweep asserting only that output holds no NaN and no infinity is satisfied by a function that returns a constant, and a green suite, full line coverage and that sweep all passed at once over exactly that defect. For a user-facing surface, the check must exercise the running surface end to end - drive the UI (browser automation where available) or invoke the real CLI; a unit test alone does not close a user-facing task. A finding judged not worth fixing goes under Declined with a one-line reason and the command or measurement that establishes that reason, written as `Derivation: <command>` on the same line - a Declined premise is a claim the declaration rests on, the declaring iteration re-runs it, the evaluator re-derives it, and the Stop hook refuses a declaration over an entry with none; never re-file a Declined item. Not worth fixing is priced, not felt: a Low whose class is not runtime and whose fix plus its regression test cannot be completed inside one iteration is by policy not worth fixing, so move it to Declined with the reason `cost: exceeds one iteration` and name it by ID in the run report; that pricing outranks the splitting rule above, because splitting such a Low into two one-iteration tasks is exactly how the price gets evaded. That is a Declined reason and never a severity change; severity is set by the rubric and the envelope alone, and downgrading a finding to reach convergence is a violation.

Class rules: when a finding is one instance of a repeatable idiom - a type guard, a parse, an escape, an error path - file and fix the class, not the instance. The fix's acceptance check must include an enumeration, a grep or AST listing of every site where the idiom appears, and every site must be covered or explicitly settled. Record each closed or declined class as one line under Settled classes in BACKLOG.md. Three-strike rule: the third finding sharing one root cause with two earlier findings ends instance work; replace it with either one structural task that closes the class at a boundary or one Proposed envelope decision, and never patch a fourth instance.

Working rules, each of them learned by losing an iteration to it: an inventory row's scope line names the enumeration command that defines it - the grep, the listing, the glob - never prose, because a scope nobody can re-run is a scope nobody can check; a removal task greps the docs for the removed names in the same iteration; a fix iteration runs the filed reproduction as its first command, because backlog lines are hypotheses that rot as sibling fixes land around them; and a hash written into a state file is copied from rev-parse output, never typed. Two clauses govern prose claims, learned from a run where four of six findings falsified sentences the run's own fixes wrote: a claim that generalises over a set of sites ships with the enumeration of that set in the same iteration, its executing check drives every enumerated site, and where the class is about failures the enumeration is built by provoking a failure at every step of the operation, never by grepping the source for the calls it makes - a step that fails without naming a syscall is invisible to a name scan; if the enumeration cannot be produced this iteration, narrow the sentence to the single site actually verified. And a fix re-executes the claims it invalidates, not only the ones it writes: before the checkpoint, re-run the checks behind every prose claim and stated number in the state files and in the modules this iteration's diff touches and their direct siblings - bounded exactly there, or this rule becomes the ledger churn the closeout rule exists to stop. Never write a line number into a state file; state the shape the enumerating command returns.

Closeout: a run that has produced one full fresh-evidence audit scoring zero High and zero Medium in-envelope stops auditing for the rest of the run, works or declines whatever is already on the ledger, and converges. Without that stop a project with a long tail of Low findings never finishes: the ledger drains, the drain triggers a replenishing audit, the audit files another Low, and the loop is productive forever without ever being done. The stop is safe because reaching it requires an audit that just came back clean of High and Medium; a High or Medium found while executing a task is still filed and still worked, and both the evaluator gate and the next run's fresh audit remain in force.

Audit discipline: the audit procedure is exactly what this Method prescribes. Never escalate rigor unilaterally - no improvised sub-auditor panels, no fuzzing campaigns, no dimensions beyond the Goal's list; the single convergence evaluator defined in the Definition of done is the only sub-agent review this Method authorizes. A case for more rigor is a Proposed item naming its cost; the user decides. Never file a finding inside a class recorded under Settled classes unless the code implementing that class changed after settlement. A finding a previous full audit scored clean, on code unchanged since, needs new evidence - a reproduced failure - not a deeper reading of the same lines. Before scoring Testing clean, run at least one test module in isolation, the cheapest first: a suite that is only ever run whole hides both order dependence and tests that pass on state a different module leaked, and neither shows up in coverage, in the pass count, or in a reverse-order run. A finding filed from an isolated run is about the test, not the runtime, unless new runtime evidence appears.

## Constraints
- Do not change public interfaces or observable behavior without recording the rationale in JOURNAL.md.
- Do not weaken security, weaken or delete tests, or remove features to make a metric pass.
- Full implementations only. A placeholder or stub written to satisfy an acceptance check is a violation, not progress.
- A task is done only when its acceptance check has been run and observed to pass. Evidence over assertion, always.
- Prefer deletion and simplification over addition. No speculative abstractions, options, or features.
- Match the project's existing conventions. No wholesale reformatting or cosmetic churn.
- Prefer well-maintained, widely adopted libraries. No heavy dependencies for trivial problems.
- Keep each change atomic. The per-iteration checkpoint commit is the revert unit; never push, never create branches, and never rewrite checkpoint history.

## Lessons
Operational rules future iterations must obey, learned during runs. One line each: a build quirk, a command that must or must not be used, a mistake made twice. When a JOURNAL Learnings line states a rule future iterations need, copy it here as one line. The project owner can add lines here too, to steer every future run: fix the loop, not the run. Keep it brief; never write status reports, run narration, or task state here. A Lesson recording its second occurrence is marked `[recurred]`, and the run report proposes promoting it to a mechanism - a hook check or a Method rule - for the user to decide: a rule that had to be written twice is a rule this text is not enforcing.

## Definition of done
Convergence requires a full audit pass, executed in one iteration, that rescores every applicable dimension against the severity rubric and the Operating envelope with fresh evidence and finds zero High and zero Medium in-envelope findings, requires that the Surface inventory lists no unswept row - a converged project is one whose whole mapped surface has actually been examined, enforced mechanically by the Stop hook - and it leaves no High and no Medium behind: at convergence the Now, Next, and Later sections of BACKLOG.md hold no open High or Medium task, because each has been completed, moved to Declined with a genuine not-worth-fixing reason, or blocked with its reason recorded. An open Low does not block a declaration - it is carried: the declaring entry lists each carried Low by ID with one line, the run report repeats them, and the published receipt names them, so the debt is visible rather than buried. The Stop hook reads severity from the task line's own `(<Severity>, ...)` form and treats a line with no parseable severity as blocking, so the floor cannot be gamed by omitting the label; the evaluator re-scores every open and carried finding against the rubric, a misscoring is itself a REJECT reason, and an accurately scored open Low is never one. A converged project is one with no defect worth an iteration left in it, and every smaller finding on the record. A `- [~]` row - surface this host cannot reach, carrying its reason - is not an unswept row and does not block convergence, but the run report names every one of them. When the closing audit itself files new findings the run is not yet converged: execute them in the following iterations and declare convergence once no High or Medium is left open, provided the only commits since that clean audit are the fixes for tasks it or the evaluator gate filed plus loop state edits and the Verify command exits 0 in the declaring iteration with its output recorded in the JOURNAL entry; if anything else changed, audit again. Proposed items never block convergence. Partial or replenishment audits never count toward convergence. Inside the one-time closing extension the Stop hook grants at budget exhaustion, one convergence shape is legal and only one: the clean full audit a declaration cites predates the window, and the window itself buys the evaluator gate, the fixes that gate files under the one-transaction rule, and the declaration. A run that arrives there without that audit on record cannot produce one inside the window; the hook ends it out of budget and convergence falls to the next run's fresh audit. Convergence also requires the adversarial evaluator gate: exactly one fresh-context sub-agent, spawned carrying none of the run's context, re-runs the Verify command and the closed tasks' acceptance checks, hunts for missed in-envelope High or Medium findings in the run's changes, and must return PASS, recorded in the JOURNAL entry of the iteration that ran it, and must leave an artifact: before returning any verdict the evaluator writes `.jeffy/evaluator/<run-id>-<n>.md`, where n is the invocation ordinal within this run, naming every command it ran with that command's real exit status, and the Stop hook reads the highest ordinal on record and refuses a PASS for which no artifact exists there, committed and unmodified. The ordinal is what makes the gate's record durable: keyed by run id alone, every re-invocation overwrote its predecessor, so a run that spent three invocations published one verdict and a squash, a rebase or a shallow clone reduced the forensic record to whatever came last. Who wrote that file cannot be proven at the shell layer and the rule does not pretend otherwise; what it changes is the price of a false PASS, from eleven typed characters to a fabricated forensic record that the checkpoint commits and the repository keeps. The artifact names any location outside the repository by a placeholder it defines once - `$SCRATCH` for the session scratch directory - and never contains a machine-absolute path: the receipt's audience is a clone, and a path only one machine can resolve is not evidence there. A PASS whose closing conditions already hold declares in its own iteration: a gate observation that is not a REJECT reason is recorded in the run report and the next run's ledger, never fixed inside the convergence sequence, because a fix after a PASS invalidates the PASS and spends an invocation the declaration needs. A PASS that does not declare in the same iteration does not carry forward, and the declaring iteration re-invokes the gate so its closing entry records the verdict the Stop hook reads there; a REJECT files its evidenced reasons as ordinary tasks and the run continues, at most 2 evaluator invocations per run and 3 when the first landed before the midpoint of the budget, (the third invocation is reachable through a PASS that could not declare in its own iteration and is re-invoked at the declaration, and equally after a second REJECT wherever the cap is 3, which is what lets a run whose first verdict was REJECT - the run that most needs the extra invocation - reach the one it earned) the cap is absolute and a third REJECT ends the declaration path outright, but what is terminal is a REJECT with no invocation remaining rather than the second one as such: a second REJECT holding an invocation files its findings and the run continues, closing every finding both rejections filed in dedicated iterations before that last invocation is spent. A terminal REJECT does not end the run while budget remains - it enters gate salvage, working only the findings the gate filed, never re-invoking, never declaring, never auditing or replenishing, and ending blocked at budget exhaustion or as soon as no gate-filed finding is left open, with the run report line `blocked - N gate findings closed, declaration deferred`. Convergence then waits for the next run's fresh gate. Three blocked runs once held 13 budgeted iterations they were forbidden to use while the gate's reproduced findings sat filed with their acceptance checks written, and each block also cost a human relaunch, and when sub-agent spawning is unavailable the run records Evaluator: unavailable with the reason in the closing entry and the run report and ends blocked - the gate is not optional and no convergence rests on its absence, so the declaration waits for a relaunch in a session where a sub-agent can be spawned. The gate is not only a closing ceremony: when the ledger first empties with a clean full audit already recorded this run and at least 3 iterations remaining, run it that iteration rather than at the declaration, because a REJECT files tasks and answering them needs budget the last iteration no longer has. The ratchet never invokes the evaluator. Severity is set by the rubric and the envelope alone: downgrading a finding to reach convergence is a violation, and Declined items must be genuinely not worth fixing, not deferred work. Pricing is how not worth fixing is judged: a Low whose class is not runtime and whose fix plus its regression test does not fit in one iteration goes to Declined with the reason `cost: exceeds one iteration`, named by ID in the run report - a Declined reason, never a lower severity. Every run ends with a run report to the user - converged, out of budget, or blocked - listing iterations used, tasks closed with severities, the run's diffstat, blocked and Proposed items, and the final Verify status. Record the closing scores and their evidence in JOURNAL.md, and, when the project is a git repository, append a line reading Converged: <full commit hash> - <date> under the ## Converged section of BACKLOG.md, before claiming convergence. That hash must be reachable from HEAD and the Stop hook checks it: a commit that merely resolves proves nothing, because an orphan left by a rebase, an abandoned branch tip and a commit fetched from elsewhere all resolve, and a receipt whose Converged hash does not resolve on a clone cannot be verified by anyone. A history rewrite that preserves the tree is answered by appending `Converged: <new hash> - <date> (repoints <old hash>, tree unchanged)` beneath the line it supersedes - legal only when the two commits carry the same tree, with the superseded line left standing as the only record that the rewrite happened, and a dated `## Note` in JOURNAL.md disclosing it - and never by editing the orphaned line.

Convergence ratchet: when the latest Converged line in BACKLOG.md names a commit, no open High or Medium task remains in Now, Next, or Later - carried Lows ride to the re-declaration exactly as they rode the original, since a severity-floor convergence leaves them open by design - the run carries no focus directive, and nothing but loop state has changed since that commit - every path in git status --porcelain and in git diff --name-only against that hash is one of PLAN.md, BACKLOG.md, JOURNAL.md, JOURNAL-archive.md, or a path under `.jeffy/`, which holds the probe batteries and is loop memory exactly as the ledger files are - verify exactly that and re-declare convergence immediately, without a fresh audit. A seeded backlog or a focus directive always gets a real audit or execution, never a ratchet. When code has changed, audit normally, but a finding in code unchanged since the convergence commit must be a reproduced in-envelope High or a regression traced to the new changes; anything else there is a Proposed item. In a project without git the ratchet degrades to the Settled classes rule alone. The iteration budget is the hard stop.
