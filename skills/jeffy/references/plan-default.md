## Goal
Raise this project to the standard a top-tier engineer would sign off on: correct on edge cases, secure by default, tested where failure hurts, simple to change, honest in its docs. Audit dimensions: architecture, code quality, security, testing, error handling, performance, documentation, dependency hygiene, developer experience, correctness, observability, and, where a user-facing surface exists, UX and accessibility. Ordering principles: correctness and security outrank polish, simplicity outranks cleverness, deleting code beats adding it, and improvement is measured by user and maintainer impact, never by activity. Leave the project materially better on every pass.

## Operating envelope
Severity is judged against this envelope, never against imagined callers. Before filing any finding, the first audit enumerates every input surface - network endpoints, CLI arguments, environment, config files, data files, state files the project writes and reads back - and classifies each with one trust class, recorded in the table below. Later audits re-read the table and must not reclassify it.

Trust classes:
- adversarial: untrusted parties can reach it (public endpoints, uploads, third-party content). The full severity rubric applies, including hostile hand-crafted input.
- user-error: the project owner hand-authors it (CLI flags, config, seed data). A wrong value deserves a clear failure message; findings about exotic malformed shapes beyond that are Low at most.
- machine-generated: the project's own pipeline produces it. The generator's real output is the contract; hand-mangled or off-contract variants are out of envelope, Low at most, Declined by default.
- state-at-rest: the project writes it and reads it back. External corruption of it is out of envelope, Low at most.

Surfaces (first audit fills this in, one line each):
- <surface>: <trust class> - <one-line reason>

Binding rules:
- A finding exercised only by out-of-envelope input is Low at most, whatever its consequence.
- Only the user widens the envelope or reclassifies a surface. An audit that believes the envelope is wrong files one Proposed item and moves on; it never files the finding at rubric severity.
- Where robustness to malformed input on a surface is genuinely wanted, the remedy is one structural task - a single validation boundary where that input enters - never scattered per-site guards.

## Surface inventory
The audit's map, and the run's bound. Before filing any finding, the first audit enumerates the project's whole public surface - every public module, class group, entry point, or command a user can reach - as one checkbox row each, listed completely before any row is explored in depth. Enumerate from the code, not from the documentation: every source file belongs to some row, including underscore-private modules that implement public behavior, because dead or orphaned code that no entry point reaches is exactly what a call-path sweep never visits. Size rows so one checkbox certifies a comparable amount of surface: a module with dozens of public functions gets several rows split by function family, never one, or the rows-swept count overweights trivial rows and a single checkbox quietly stands for half the project. A row starts unswept: `- [ ] <surface>: <scope>`. An executed probe, and only an executed probe, flips it: `- [x] <surface>: swept at <commit> - <what the sweep exercised>`. A row whose implementing code changes after its recorded commit is stale: flip it back to unswept, because the old sweep no longer certifies the new code.

For a surface that computes values, a probe is a correctness check, not a liveness check. Sweeping such a row requires at least one known-answer test per function family it covers - a closed form, a hand-computed small case, or an independent reference implementation - or a strong invariant that a wrong result would break. Run-without-crashing flips nothing there: the costliest defects return wrong numbers without complaint, and a crash-biased sweep files every type error while certifying wrong arithmetic as clean. A metric off by a constant factor, a parameter silently ignored, and an aggregation that quietly no-ops all pass a liveness probe and all fail a known-answer one.

A sweep also exercises every documented parameter of the functions it certifies, at two or more values that must change the output, including the negative or boundary side of the domain where one exists. A documented parameter whose value changes nothing is a finding, never a pass, unless the documentation itself says it should have no effect in that case. This is a recurring class, not a corner: an inert flag, a rate applied only when positive, and an aggregation token falling through to no-op are the same defect wearing three names, and a sweep that probes a parameter only where it works will certify the row while the parameter is dead everywhere else.

Dimension scores claim only swept rows. A None on a dimension whose surface still has unswept rows is silence, not cleanliness, and an audit that presents such a score as the whole project is the failure this table exists to prevent: a library scored correctness None across five audits while an entire simulation module sat unexamined, and every audit's new High was simply the next unvisited room. The first audit therefore probes breadth-first - every row shallowly before any row deeply - so the worst defect in the project appears in the first filing, not the sixth.

Convergence requires that this table lists no unswept row, and the Stop hook checks that mechanically. That is what makes the loop bounded: the surface is finite, sweeps only accumulate, and the remaining work is always the visible remainder of a written list rather than a hope that the next audit comes back empty. The run report states progress as rows swept of rows total.

- [ ] <surface>: <scope>

## Method
Audit the project against every applicable dimension and score each by its highest finding severity: High, Medium, Low, or None. Skip dimensions that do not apply and record why. Every audit consults the Surface inventory first and sweeps unswept or stale rows before re-probing swept ones; an audit never wanders. When replenishing with a partial audit, target the dimensions least recently scored and the inventory rows least recently swept.

Severity rubric - judge by consequence, not by effort to fix:
- High: users get wrong results, data loss or corruption, a security vulnerability, a crash on realistic in-envelope input, or a broken build or install.
- Medium: failure on a plausible in-envelope edge case, a silently swallowed error, missing tests on a path whose failure would matter, misleading documentation, or a dependency with a known vulnerability.
- Low: polish - naming, style, minor docs, cosmetic gaps.

Evidence rule: a finding exists only if you can point at it - a file and line, a failing command, or a reproduced behavior. Verify before filing; no speculative findings. File the root cause, not each symptom.

Publication rule: code that leaves this project - an issue body, a pull request description, a report, a message to anyone - must be run in exactly the form it is published, and its stated output must be that run's real output. Trimming a working script down to something shorter and clearer does not inherit the original's verification: a reduction is new code, and it is unverified until it has been executed as written. Verifying one artifact and shipping a different one is the failure this rule exists to stop, and it is expensive, because the person who finds the broken version is the person whose trust was being asked for.

Write findings into BACKLOG.md as prioritized checkable tasks, worst severity first: High in Now, Medium in Next, Low in Later; break ties by user impact, then by smallest effort. Every task must be completable in a single iteration - split it if not - and must carry an acceptance check that is a runnable command or an observable fact, never an opinion. An acceptance check must be strong enough to fail: run it against the unfixed code and confirm that it does, because a check the broken implementation also satisfies proves nothing. Prefer a differential or invariant assertion over an absence-of-badness one - a sweep asserting only that output holds no NaN and no infinity is satisfied by a function that returns a constant, and a green suite, full line coverage and that sweep all passed at once over exactly that defect. For a user-facing surface, the check must exercise the running surface end to end - drive the UI (browser automation where available) or invoke the real CLI; a unit test alone does not close a user-facing task. A finding judged not worth fixing goes under Declined with a one-line reason; never re-file a Declined item.

Class rules: when a finding is one instance of a repeatable idiom - a type guard, a parse, an escape, an error path - file and fix the class, not the instance. The fix's acceptance check must include an enumeration, a grep or AST listing of every site where the idiom appears, and every site must be covered or explicitly settled. Record each closed or declined class as one line under Settled classes in BACKLOG.md. Three-strike rule: the third finding sharing one root cause with two earlier findings ends instance work; replace it with either one structural task that closes the class at a boundary or one Proposed envelope decision, and never patch a fourth instance.

Closeout: a run that has produced one full fresh-evidence audit scoring zero High and zero Medium in-envelope stops auditing for the rest of the run, works or declines whatever is already on the ledger, and converges. Without that stop a project with a long tail of Low findings never finishes: the ledger drains, the drain triggers a replenishing audit, the audit files another Low, and the loop is productive forever without ever being done. The stop is safe because reaching it requires an audit that just came back clean of High and Medium; a High or Medium found while executing a task is still filed and still worked, and both the evaluator gate and the next run's fresh audit remain in force.

Audit discipline: the audit procedure is exactly what this Method prescribes. Never escalate rigor unilaterally - no improvised sub-auditor panels, no fuzzing campaigns, no dimensions beyond the Goal's list; the single convergence evaluator defined in the Definition of done is the only sub-agent review this Method authorizes. A case for more rigor is a Proposed item naming its cost; the user decides. Never file a finding inside a class recorded under Settled classes unless the code implementing that class changed after settlement. A finding a previous full audit scored clean, on code unchanged since, needs new evidence - a reproduced failure - not a deeper reading of the same lines.

## Constraints
- Do not change public interfaces or observable behavior without recording the rationale in JOURNAL.md.
- Do not weaken security, weaken or delete tests, or remove features to make a metric pass.
- Full implementations only. A placeholder or stub written to satisfy an acceptance check is a violation, not progress.
- A task is done only when its acceptance check has been run and observed to pass. Evidence over assertion, always.
- Prefer deletion and simplification over addition. No speculative abstractions, options, or features.
- Match the project's existing conventions. No wholesale reformatting or cosmetic churn.
- Prefer well-maintained, widely adopted libraries. No heavy dependencies for trivial problems.
- Keep each change atomic. The per-iteration checkpoint commit is the revert unit; never push, never create branches, and never rewrite checkpoint history.

## Definition of done
Convergence requires a full audit pass, executed in one iteration, that rescores every applicable dimension against the severity rubric and the Operating envelope with fresh evidence and finds zero High and zero Medium in-envelope findings, requires that the Surface inventory lists no unswept row - a converged project is one whose whole mapped surface has actually been examined, enforced mechanically by the Stop hook - and it leaves no open task behind: at convergence the Now, Next, and Later sections of BACKLOG.md are empty, because every filed finding, Low included, has been completed, moved to Declined with a genuine not-worth-fixing reason, or blocked with its reason recorded and named in the run report. A converged project is completely done, not done except the small stuff. When the closing audit itself files new findings the run is not yet converged: execute them in the following iterations and declare convergence once the backlog is empty again, provided the only commits since that clean audit are those fixes plus loop state edits and the Verify command exits 0 in the declaring iteration with its output recorded in the JOURNAL entry; if anything else changed, audit again. Proposed items never block convergence. Partial or replenishment audits never count toward convergence. Convergence also requires the adversarial evaluator gate: exactly one fresh-context sub-agent, spawned carrying none of the run's context, re-runs the Verify command and the closed tasks' acceptance checks, hunts for missed in-envelope High or Medium findings in the run's changes, and must return PASS, recorded in the closing JOURNAL entry; a REJECT files its evidenced reasons as ordinary tasks and the run continues, at most 2 evaluator invocations per run, a second REJECT ends the run as a hard blocker, and when sub-agent spawning is unavailable the run records Evaluator: unavailable with the reason and may converge under the remaining conditions. The ratchet never invokes the evaluator. Severity is set by the rubric and the envelope alone: downgrading a finding to reach convergence is a violation, and Declined items must be genuinely not worth fixing, not deferred work. Every run ends with a run report to the user - converged, out of budget, or blocked - listing iterations used, tasks closed with severities, the run's diffstat, blocked and Proposed items, and the final Verify status. Record the closing scores and their evidence in JOURNAL.md, and, when the project is a git repository, append a line reading Converged: <full commit hash> - <date> under the ## Converged section of BACKLOG.md, before claiming convergence.

Convergence ratchet: when the latest Converged line in BACKLOG.md names a commit, no open task remains in Now, Next, or Later, the run carries no focus directive, and nothing but loop state has changed since that commit - every path in git status --porcelain and in git diff --name-only against that hash is one of PLAN.md, BACKLOG.md, JOURNAL.md, or JOURNAL-archive.md - verify exactly that and re-declare convergence immediately, without a fresh audit. A seeded backlog or a focus directive always gets a real audit or execution, never a ratchet. When code has changed, audit normally, but a finding in code unchanged since the convergence commit must be a reproduced in-envelope High or a regression traced to the new changes; anything else there is a Proposed item. In a project without git the ratchet degrades to the Settled classes rule alone. The iteration budget is the hard stop.
