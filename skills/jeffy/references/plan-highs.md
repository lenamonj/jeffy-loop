# Plan

## Mode
High-hunt. Auto-generated by /jeffy --highs. The loop audits the whole surface, fixes only Highs, audits again once no High is open, and closes the first time an audit finds none. There is no sweep obligation, no Medium or Low queue, no evaluator gate, no closing extension and no convergence claim; a standard launch over this file is refused, and a hunt launch over a standard PLAN.md is refused the same way.

## Goal
Find and fix every High a user of the shipped product meets - wrong results, data loss or corruption, a security vulnerability, a crash on realistic in-envelope input, or a broken build or install a user performs - and nothing below it. Audit dimensions: architecture, code quality, security, testing, error handling, performance, documentation, dependency hygiene, developer experience, correctness, observability, and, where a user-facing surface exists, UX and accessibility. Ordering principles: correctness and security outrank everything else, simplicity outranks cleverness, deleting code beats adding it, and a hunt is measured by the Highs it closes, never by activity. A Medium or Low the audit notices is recorded and left alone.

## Operating envelope
Severity is judged against this envelope, never against imagined callers. Before filing any finding, the first audit enumerates every input surface - network endpoints, CLI arguments, environment, config files, data files, state files the project writes and reads back - and classifies each with one trust class, recorded in the table below. Later audits re-read the table and must not reclassify it.

Trust classes:
- adversarial: untrusted parties can reach it (public endpoints, uploads, third-party content). The full severity rubric applies, including hostile hand-crafted input.
- user-error: the project owner hand-authors it (CLI flags, config, seed data). A wrong value deserves a clear failure message; findings about exotic malformed shapes beyond that are Low at most.
- machine-generated: the project's own pipeline produces it. The generator's real output is the contract; hand-mangled or off-contract variants are out of envelope, Low at most, Declined by default.
- state-at-rest: the project writes it and reads it back. External corruption of it is out of envelope, Low at most.

Surfaces (first audit fills this in, one line each):
- <surface>: <trust class> - <one-line reason>

Binding rules:
- A finding exercised only by out-of-envelope input is Low at most, whatever its consequence.
- Only the user widens the envelope or reclassifies a surface. An audit that believes the envelope is wrong files one Proposed item and moves on; it never files the finding at rubric severity.
- Where robustness to malformed input on a surface is genuinely wanted, the remedy is one structural task - a single validation boundary where that input enters - never scattered per-site guards.

## Surface inventory
The audit's map. Before filing any finding, the first audit enumerates the project's whole public surface - every public module, class group, entry point, or command a user can reach - as one checkbox row each, listed completely before any row is explored in depth. Enumerate from the code, not from the documentation: every source file belongs to some row, including underscore-private modules that implement public behavior, because dead or orphaned code that no entry point reaches is exactly what a call-path sweep never visits. Size rows so one row stands for a comparable amount of surface: a module with dozens of public functions gets several rows split by function family, never one. A row is written `- [ ] <surface>: <scope>` and stays that way: a hunt does not sweep rows and never flips one, the inventory is the map every audit walks, and the close does not require a swept row. A third state exists for surface this host cannot reach at all - a platform-only build, a service that cannot be installed here: `- [~] <surface>: unreachable on this host - <reason>`. It is a disclosure, not a probe, and the run report names every one of them.

For a surface that computes values, a probe is a correctness check, not a liveness check. Walking such a row requires at least one known-answer test per function family it covers - a closed form, a hand-computed small case, or an independent reference implementation - or a strong invariant that a wrong result would break. Run-without-crashing proves nothing there: the costliest defects return wrong numbers without complaint, and a crash-biased probe files every type error while certifying wrong arithmetic as clean. A metric off by a constant factor, a parameter silently ignored, and an aggregation that quietly no-ops all pass a liveness probe and all fail a known-answer one. Keep the instrument: write it under `.jeffy/probes/<row-slug>` so the iteration checkpoints commit it, and a later audit re-runs that battery instead of rebuilding it. A battery is updated in the same iteration as the behavior it pins. A battery may declare the paths it covers in `.jeffy/probes/<row-slug>/paths`, one glob per line relative to the project root; an iteration whose diff touches a declared path runs that battery in the same iteration and treats a failure exactly as it treats a Verify failure. A battery that certifies content records, at its creation, the discriminating input or pre-fix tree state it was once observed failing on, because an instrument that has never been seen to fail reads exactly like an instrument that passed. A battery README states a measurement only as the summary line its battery prints (`<battery>: x/y checks passed`), and that line is the `<value>` of a line `expect <value> :: <command>` in the battery's claims file, measured off a real run; `N checks red` is a count no command returns and is refused. Batteries and probes execute through the installed `skills/jeffy/hooks/lib/run-probe.sh` beside the verify wrapper, which bounds an instrument's memory and wall time so a runaway probe dies alone instead of taking the run with it; a probe killed at the ceiling is an instrument finding about the probe, never a reason the iteration ends.

An audit also exercises every documented parameter of the functions it probes, at two or more values that must change the output, including the negative or boundary side of the domain where one exists. A documented parameter whose value changes nothing is a finding, never a pass, unless the documentation itself says it should have no effect in that case: an inert flag, a rate applied only when positive, and an aggregation token falling through to no-op are the same defect wearing three names.

Dimension scores claim only rows the audit walked. A None on a dimension whose rows were never opened is silence, not cleanliness, so every audit probes breadth-first - every row shallowly before any row deeply - and the worst defect in the project appears in the first filing, not the sixth. The run report states the map as rows walked of rows total.

Rows (first audit fills this in, one line each):
- [ ] <surface>: <scope>

## Verify command
One runnable command that must exit 0 for this project to count as unbroken - the test suite, the build, or a validator script. The first audit fills this in; write none with a one-line reason only if the project genuinely has no runnable gate. It runs at the end of every iteration: a failure the previous checkpoint did not have means the iteration broke the project, and the iteration is reverted.

An exit status is a narrow thing to trust, so the same first audit writes down what that status actually covers. `Oracle class` names what the command grades, in your own words: unit tests, a conformance corpus, a differential comparison against a reference implementation, a build only. `Environment fingerprint` names the platform, the toolchain versions, and every test target this platform excludes - and that exclusion list is derived by a command, enumerating the build constraints, platform guards and skip markers in the test tree, with the line naming the command that produced it. Never a bare assertion that nothing is excluded: the whole failure this exists to catch is an exclusion nobody looked for. The declaring iteration re-reads both lines, and a test asset the fingerprint says the command cannot reach is one no journal entry may claim was green. A run once converged over 29 iterations while its project's 402-case conformance corpus never executed at all - the only file importing it carried a build tag for another platform, and the command's own package selection never reached it - and that run asserted twice that the corpus was passing. Nothing mechanical could catch it, because the command exited 0 every time; only the declaration could have.

The gate is run through the installed `skills/jeffy/hooks/lib/quiet-verify.sh` (the launch banner names its absolute path), never as the raw command, and the reason is context rather than convenience: a green suite prints its whole passing output into the window every iteration, in a session where context already accumulates - the engine's own validator is hundreds of lines of `OK` on a green run. Through the wrapper a green run prints nothing to stdout and one line to stderr; a red run prints its last `Verify output budget` lines, default 80; a timeout is a failure. Silence must not cost the record, though, because journal entries and receipts quote real verify counts: `Verify summary pattern` names a regex, and the single line of output matching it rides the green line so the figure stays quotable. The wrapper also refuses a `PLAN.md` whose `Oracle class` is declared-but-empty or half-migrated, which the converged stop refuses anyway - the difference is that the run finds out at its second iteration instead of at its declaration.

The total that command grades is a measurement, not a claim, so it is written down once and by the party that took it. `quiet-verify.sh` records the figure on its own green line, and `Verify count` holds that figure and nothing else: the hook says so at every checkpoint where the two disagree and refuses a declaration on it, because a run once spent an entire evaluator invocation on an Oracle class sentence that said 1045 while the suite it described graded 1064. A number a person or a model typed is a claim; a number the wrapper computed is a measurement, and the gate should never be the first thing to compare the two.

A suite whose runtime is worth recording gets one more labeled line. `Verify duration: <N>s measured <date>` states the suite's wall time from a real timed run, and the Stop hook derives its converged-stop bound from it, resolving `verify_timeout_seconds`, else `Verify duration` x3 floored at 240s, else 240s, capped at 1740s because the installer registers the hook with an 1800s timeout, so a legitimately slow suite is not refused at the declaration for outrunning a bound nobody measured; the launcher reads the same line so a relaunch inherits the bound. Record it when a timed run shows the suite near or past four minutes, and update it in the same iteration as any change that moves the measurement materially.

Command: <first audit fills this in>
Oracle class: <first audit fills this in>
Environment fingerprint: <first audit fills this in>
Verify duration: <optional; from a timed run, when the suite runs near or past four minutes>
Verify output budget: <optional; lines of failing output the wrapper prints, default 80>
Verify summary pattern: <optional; regex matching the one result line worth quoting, e.g. [0-9]+ (passed|OK)>
Verify count: <optional; the total the summary line reports, filled by the first audit from a real run and kept equal to the wrapper's last green total - never a typed number. The wrapper reads the FIRST integer on the line its summary pattern matched, so leave this empty where that integer is not the total, and the check stays silent rather than nagging>

Stated counts: a count this file or BACKLOG.md states in prose is written as `returns <count>` and carries a row `label|<count>|<command>` in the table below, which `skills/jeffy/hooks/lib/check-claims.sh` executes beside the battery claims; a stated count the table does not carry refuses the declaration, and a number word above fifty or any compound is refused as unvalued rather than passed. Inventory rows and the Declined and Settled classes sections are outside this rule, because their counts are the evidence of some other instrument. `returns 0` is read as an exit status, never as a count. A row whose command prints `unavailable:<why>` is skipped on that host, not faulted. A file with no table, or a table with no rows yet, states no counts this way: the first row arms the check, and the first audit is where the rows are written.

## Method
Audit the project against every applicable dimension and score each by its highest finding severity: High, Medium, Low, or None. Skip dimensions that do not apply and record why. Every audit walks the Surface inventory in full and never wanders. A hunt runs exactly two kinds of audit: the first one, and a fresh full one each time no High is open; there is no partial or replenishing audit.

Severity rubric - judge by the consequence a user of the shipped product meets, never by effort to fix:
- High: users get wrong results, data loss or corruption, a security vulnerability, a crash on realistic in-envelope input, or a broken build or install a user performs.
- Medium: failure on a plausible in-envelope edge case, a silently swallowed error, a documented promise the code does not keep, a published artifact carrying what it should not, or a dependency with a known vulnerability.
- Low: polish - naming, style, minor docs, cosmetic gaps - and everything a user of the shipped product never meets: missing or weak tests, lint, formatting, type-checker output, CI configuration, developer tooling, coverage.

Severity ceiling by class: a High or Medium names what a user of the shipped product meets. A task of class test or dev-tooling is Low, always, because the user never runs it. A High or Medium of class docs or build-ci carries `Consequence: <what a user of the shipped product meets>` on its line - a documented promise the code does not keep, an install a user performs that fails, a published artifact carrying the wrong contents - and a line that cannot state one is a Low. The Stop hook refuses the close over a task this run filed that breaks either rule; lines carried from earlier runs are re-scored under this rubric by the audit, not refused. This is the bar that keeps a run pointed at the product: a run spends its iterations on what users meet, and a suite's gaps, a linter's output and a CI job's colour are reported, never chased.

Evidence rule: a finding exists only if you can point at it - a file and line, a failing command, or a reproduced behavior. Verify before filing; no speculative findings. File the root cause, not each symptom.

Publication rule: code that leaves this project - an issue body, a pull request description, a report, a message to anyone - must be run in exactly the form it is published, and its stated output must be that run's real output. Trimming a working script down to something shorter and clearer does not inherit the original's verification: a reduction is new code, and it is unverified until it has been executed as written. Verifying one artifact and shipping a different one is the failure this rule exists to stop, and it is expensive, because the person who finds the broken version is the person whose trust was being asked for.

Write findings into BACKLOG.md as prioritized checkable tasks, Highs only, in Now, worst first; break ties by user impact, then by smallest effort. A Medium or Low the audit notices is recorded in that AUDIT entry on one line beginning `Noted, not filed:` with one clause per finding, never on the ledger and never worked; the run report and the published receipt repeat those lines, so what the hunt saw and left is visible rather than buried. Each line names its class: `- [ ] <ID> (High, <class>, <dimension>): <finding>. Acceptance: <check>.` - class is one of runtime, test, build-ci, docs, dev-tooling, chosen by the files the fix will touch; a High of class docs or build-ci adds `Consequence: <what a user of the shipped product meets>.` before its Acceptance, per the severity ceiling by class, and a High of class test or dev-tooling cannot exist under that ceiling. Every task must be completable in a single iteration - split it if not - and must carry an acceptance check that is a runnable command or an observable fact, never an opinion. An acceptance check must be strong enough to fail: run it against the unfixed code and confirm that it does, because a check the broken implementation also satisfies proves nothing. Prefer a differential or invariant assertion over an absence-of-badness one. For a user-facing surface, the check must exercise the running surface end to end - drive the UI (browser automation where available) or invoke the real CLI; a unit test alone does not close a user-facing task. A High judged not worth fixing goes under Declined with a one-line reason and the command or measurement that establishes that reason, written as `Derivation: <command>` on the same line - a Declined premise is a claim the close rests on, the closing iteration re-runs it, and the Stop hook refuses a close over an entry with none; never re-file a Declined item. Severity is set by the rubric and the envelope alone: filing a High as a Medium to leave it, or a Medium as a High to work it, is a violation.

Class rules: when a High is one instance of a repeatable idiom - a type guard, a parse, an escape, an error path - fix the class, not the instance, and the fix's acceptance check includes an enumeration, a grep or AST listing of every site where the idiom appears, with every site covered. Three-strike rule: the third finding sharing one root cause with two earlier findings ends instance work; replace it with either one structural task that closes the class at a boundary or one Proposed envelope decision, and never patch a fourth instance.

Working rules, each of them learned by losing an iteration to it: an inventory row's scope line names the enumeration command that defines it - the grep, the listing, the glob - never prose, because a scope nobody can re-run is a scope nobody can check; a removal task greps the docs for the removed names in the same iteration; a fix iteration runs the filed reproduction as its first command, because backlog lines are hypotheses that rot as sibling fixes land around them; and a hash written into a state file is copied from rev-parse output, never typed. Two clauses govern prose claims, learned from a run where four of six findings falsified sentences the run's own fixes wrote: a claim that generalises over a set of sites ships with the enumeration of that set in the same iteration, its executing check drives every enumerated site, and where the class is about failures the enumeration is built by provoking a failure at every step of the operation, never by grepping the source for the calls it makes - a step that fails without naming a syscall is invisible to a name scan; if the enumeration cannot be produced this iteration, narrow the sentence to the single site actually verified. And a fix re-executes the claims it invalidates, not only the ones it writes: before the checkpoint, re-run the checks behind every prose claim and stated number in the state files and in the modules this iteration's diff touches and their direct siblings - bounded exactly there, or this rule becomes the ledger churn the closeout rule exists to stop. Never write a line number into a state file; state the shape the enumerating command returns.

Audit discipline: the audit procedure is exactly what this Method prescribes. Never escalate rigor unilaterally - no improvised sub-auditor panels, no fuzzing campaigns, no dimensions beyond the Goal's list, and no sub-agent review at all: a hunt has no evaluator gate, and its close rests on the fresh audit alone, which is why that audit is full and fresh every time. A case for more rigor is a Proposed item naming its cost; the user decides. A finding a previous full audit scored clean, on code unchanged since, needs new evidence - a reproduced failure - not a deeper reading of the same lines.

## Constraints
- Do not change public interfaces or observable behavior without recording the rationale in JOURNAL.md.
- Do not weaken security, weaken or delete tests, or remove features to make a metric pass.
- Full implementations only. A placeholder or stub written to satisfy an acceptance check is a violation, not progress.
- A task is done only when its acceptance check has been run and observed to pass. Evidence over assertion, always.
- Prefer deletion and simplification over addition. No speculative abstractions, options, or features.
- Match the project's existing conventions. No wholesale reformatting or cosmetic churn.
- Prefer well-maintained, widely adopted libraries. No heavy dependencies for trivial problems.
- Keep each change atomic. The per-iteration checkpoint commit is the revert unit; never push, never create branches, and never rewrite checkpoint history.

## Lessons
Operational rules future iterations must obey, learned during runs. One line each: a build quirk, a command that must or must not be used, a mistake made twice. When a JOURNAL Learnings line states a rule future iterations need, copy it here as one line. The project owner can add lines here too, to steer every future run: fix the loop, not the run. Keep it brief; never write status reports, run narration, or task state here. A Lesson recording its second occurrence is marked `[recurred]`, and the run report proposes promoting it to a mechanism - a hook check or a Method rule - for the user to decide: a rule that had to be written twice is a rule this text is not enforcing.

## Definition of done
The hunt is complete when a full fresh-evidence audit, executed in one iteration, rescores every applicable dimension against the severity rubric and the Operating envelope with fresh evidence and finds zero High in-envelope findings, and no open High remains in BACKLOG.md: each High filed this run has been completed, moved to Declined with a genuine not-worth-fixing reason and its Derivation, or blocked with its reason recorded, and a blocked High is named in the run report. The Stop hook reads severity from the task line's own `(<Severity>, ...)` form and refuses the close over any open line that is not a High, because a hunt ledger carries Highs only, and over a line with no parseable severity, so the floor cannot be gamed by omission. The audit that finds no High and the close share one iteration: that AUDIT entry takes status hunted, its Checkpoint field names the iteration's checkpoint commit, the only commits since the previous audit are the completed fixes for the Highs it filed plus loop state edits, the Verify command exits 0 in that iteration with its output recorded in the JOURNAL entry, and, when the project is a git repository, a line reading Hunted: <full commit hash> - <date> - <k> Highs closed is appended under the ## Hunted section of BACKLOG.md before the close is claimed, where k counts the Highs this run closed. The Stop hook refuses a close whose last AUDIT entry carries no resolvable Checkpoint, or after whose checkpoint a product path changed, because an audit that predates a fix certifies a tree that no longer exists. That hash must be reachable from HEAD and the Stop hook checks it; a history rewrite that preserves the tree is answered by appending `Hunted: <new hash> - <date> - <k> Highs closed (repoints <old hash>, tree unchanged)` beneath the line it supersedes - legal only when the two commits carry the same tree, with the superseded line left standing and a dated `## Note` in JOURNAL.md disclosing it - and never by editing the orphaned line. A hunt is not a convergence: there is no evaluator gate, no sweep requirement, no closing extension and no ratchet, the Hunted line certifies only that a fresh audit found no High at that commit, and a later run of either mode audits fresh. Proposed items never block the close. Every run ends with a run report to the user - hunt complete, out of budget, or blocked - listing iterations used, the Highs closed, every `Noted, not filed:` line, the run's diffstat, blocked and Proposed items, and the final Verify status. The iteration budget is the hard stop.
