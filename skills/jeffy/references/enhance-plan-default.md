# Plan

## Mode
Enhance. Auto-generated by /jeffy [N] enhance <topic>. This run designs and builds improvements on the stated topic; it is not the defect loop, and it never files defect findings at severity. The standard Improvement mode is unchanged and unavailable from this PLAN.md: to run it, archive these state files and relaunch /jeffy without the keyword.

## Topic
<filled at bootstrap with the sanitized topic>

The topic bounds this run the way the Operating envelope bounds a defect run: every task must serve it, and an improvement outside it is a Proposed item, never a task. A run that cannot tie a task to the topic in one sentence does not file that task.

## Goal
Design and build improvements on the topic that a top-tier engineer would be proud to ship: better design, new capability, sharper developer experience - measured by user and maintainer impact, never by activity. Deleting and simplifying count as improvement. The first iteration is an opportunity audit: survey the topic's surface breadth-first, then file ranked enhancement tasks into BACKLOG.md, worst gap first, each with an acceptance check that can fail.

## Evidence rule
An opportunity exists only if you can point at it: a gap a named user action hits, a platform the installers support but nothing exercises, a workflow that takes five steps where a peer tool takes one, a capability the project's own docs promise adjacently and stop short of. Could-add-more-X is not an opportunity. Reproduce the gap before filing it, and name the reproduction in the task.

## Impact ranking
Rank tasks by impact in place of the defect rubric's severity - the same sections, High in Now, Medium in Next, Low in Later, the same line grammar with the rank in the severity slot:
- High impact: a capability or design change most users of the topic area would notice and value.
- Medium impact: a real improvement for a common workflow or a named class of users.
- Low impact: polish within the topic.
Pricing is unchanged: a Low-impact item whose build plus its test does not fit one iteration is by policy not worth building - moved to Declined with the reason cost: exceeds one iteration and named in the run report. Ranking is set by user and maintainer impact alone; never inflate a rank to justify work you want to do.

## Surface inventory
The opportunity audit's map, and the run's bound: enumerate the surface the topic touches - the modules, entry points, commands, and user paths involved - one checkbox row each, sized so one checkbox certifies a comparable amount of surface, listed completely before any row is explored in depth, each scope line naming the enumeration command that defines it. A row flips to swept only when an executed probe or a built-and-verified enhancement has exercised it: `- [x] <surface>: swept at <commit> - <what was exercised>`. A third state, `- [~] <surface>: unreachable on this host - <reason>`, is a disclosure, not a sweep, and every one is named in the run report. Convergence requires that this table lists no unswept row, checked mechanically by the Stop hook.

## Verify command
One runnable command that must exit 0 for this project to count as unbroken - the test suite, the build, or a validator script. The opportunity audit fills this in; write none with a one-line reason only if the project genuinely has no runnable gate. It runs at the end of every iteration: a failure the previous checkpoint did not have means the iteration broke the project, and the iteration is reverted.

## Method
Work the ledger one task per iteration, highest impact first. The standard discipline applies whole: every task completable in a single iteration or split; every acceptance check a runnable command or an observable fact, never an opinion, and run against the unimproved tree first to confirm it fails, because a check the tree already satisfies proves the enhancement was not needed or not built; for a user-facing surface the check drives the running surface end to end. Full implementations only - a stub written to satisfy a check is a violation, not progress. Match the project's existing conventions; prefer well-maintained, widely adopted libraries; no speculative abstractions beyond the topic; prefer the smallest design that serves the topic well over the largest one that shows effort. A defect discovered while building: when it blocks the task in flight, file it as one ordinary task and fix it; otherwise it is recorded in the run report for a standard run to take - never filed at severity, never allowed to widen this run into an uninvited audit. Every iteration ends in a local checkpoint commit prefixed jeffy:, journals itself under the heading grammar, and runs the Verify command.

## Constraints
- Do not change public interfaces or observable behavior without recording the rationale in JOURNAL.md.
- Do not weaken security, weaken or delete tests, or remove features to make a check pass.
- Keep each change atomic; the per-iteration checkpoint is the revert unit; never push, never create branches, never rewrite checkpoint history.

## Lessons
Operational rules future iterations must obey, learned during runs. One line each. A Lesson recording its second occurrence is marked `[recurred]`, and the run report proposes promoting it to a mechanism.

## Definition of done
Convergence means the topic is served and the tree is sound: the Now, Next, and Later sections of BACKLOG.md are empty - every filed enhancement built with its acceptance check observed to pass, moved to Declined with a priced reason, or blocked with its reason recorded and named in the run report - the Surface inventory lists no unswept row, and the Verify command exits 0 in the declaring iteration with its output recorded in the JOURNAL entry. Convergence requires the adversarial evaluator gate: exactly one fresh-context sub-agent, spawned carrying none of the run's context, re-runs the Verify command and the built enhancements' acceptance checks, hunts for regressions and half-built work in the run's changes, and must return PASS, recorded in the JOURNAL entry of the iteration that ran it and backed by the artifact the evaluator writes at `.jeffy/evaluator/<run-id>.md` naming every command it ran with that command's real exit status, under the same invocation caps, early-gate rule, artifact requirement, and REJECT consequences as the standard loop; when sub-agent spawning is unavailable the run records Evaluator: unavailable with the reason and ends blocked, because the gate is not optional in either mode. Proposed items never block convergence. Every run ends with a run report - converged, out of budget, or blocked - listing iterations used, tasks built with their impact ranks, the run's diffstat, blocked and Proposed items, defects recorded for a standard run, and the final Verify status. Record the closing evidence in JOURNAL.md and, when the project is a git repository, append a line reading Converged: <full commit hash> - <date> under the ## Converged section of BACKLOG.md, before claiming convergence.
